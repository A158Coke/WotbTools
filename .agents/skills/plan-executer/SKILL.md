# Plan Executer（计划执行）

定位：把已批准的《开发方案单》（`docs/current-plan.md`）落地为代码。
不重新讨论方案、不扩大范围、每步可独立验证。

## 输入

- `docs/current-plan.md`（必须完整读取，不要跳过任何章节）

## 流程

1. **完整读取计划**：读 `docs/current-plan.md`，确认"分步计划"状态表、
   "影响面清单"、"验收标准"、"待确认项"与"非目标"。
2. **授权校验**：待确认项中存在未确认的"阻塞"项 → 停下汇报，不执行；
   用户明确说"执行/批准"即视为已授权。
3. **创建任务分支（分支名符合任务主题）**：
   - 从计划内容提取主题：优先计划标题 /《开发方案单》标题 / 业务目标第一句；
     无标题时用影响面中最核心的动词短语。
   - 分支名规则：小写 `kebab-case`（连字符分隔），按变更类型加前缀
     `feat/` / `fix/` / `refactor/` / `chore/`；长度 ≤ 60；只用字母、数字与连字符；
     分支名须能直接看出任务主题。
   - 先 `git checkout main` + `git pull --ff-only origin main` 同步；
     若同名分支已存在（`git branch --list <pattern>`），复用并说明，或停下询问用户；
     不在 main 上直接执行。
   - `git checkout -b <branch>` 后，后续所有步骤都在该分支上完成。
4. **确定执行顺序**：按状态表顺序执行标记为"待批准/待执行"的任务；
   只执行当前计划内任务。
5. **逐项执行（每步）**：
   - 读该步文件清单与影响面，定位相关代码（用 `rg` / `rg --files`）；
   - 实现，遵循项目约定（`.agents/AGENTS.md`、`wotb-sync` 跨层检查单）；
   - 运行该步对应测试/构建验证；失败先修复再前进；
   - 更新计划状态表（进行中 → 完成），并在 commentary 简短汇报。
6. **阻塞处理**：遇到依赖用户决策、外部数据或超出计划范围的改动时，
   停下汇报并给出选项；不静默扩大范围、不自行改方案。
7. **全部完成后**：
   - 按"验收标准"逐条验证（映射到具体测试/检查，禁止口头宣称通过）；
   - 跑全量测试与构建（Java / 前端，按项目 CI 口径）；
   - 影响行为/文档时更新 `docs/CHANGELOG.md`；
   - 汇总：修改文件、测试结果、仍存在的真实限制；
   - **自动调用 review-with-docs 审查**（必须执行，不是建议）：读
     `.agents/skills/review-with-docs/SKILL.md`，对本次全部变更执行其流程
     （代码质量审查 + 文档同步 + AI 死代码清理）；审查发现的问题先修复，
     再复查直到零问题；单轮无法闭环的阻塞项停下汇报。
8. **计划文件收尾**：状态表全部置为完成；按 `current-plan.md` 头部约定
   决定清理回初始状态（默认保留完成记录，询问用户是否清理）。
   任务分支保留，用于按项目流程提 PR；PR 合并后由 `finish-task` 清理分支与计划文件。

## 规则

- 执行前必须基于最新 main 创建符合任务主题的分支，所有变更只落在该分支上；不在 main 直接执行。
- 只执行计划内任务："非目标"清单内的改动一律不做。
- 每步必须有验证，禁止"改完就继续"。
- 计划中标记"待确认"且阻塞的项，未获用户答复前不得执行。
- 发现方案与代码事实冲突时停下汇报（引用 `文件:行`），不擅自推翻已批准方案。
- 执行完成后必须调用 review-with-docs 审查并闭环（修复 → 复查 → 零问题），
  审查结果写入最终汇报；本技能不替代审查。
