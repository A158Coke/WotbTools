# Grill-Me（需求澄清）

> 定位：开发前把"模糊诉求"grill 成"可验收需求"。不写代码、不查实现；实现角度交给 grill-with-docs。

## 启动信号

- 需求是一句话/一段话，边界模糊；
- 关键词有歧义（例："复盘"指教练报告、数据回放还是功能入口）；
- 用户给的是痛点或方向，不是明确需求；
- 用户自己说"我也没想清楚 / 你先帮我分析下"。

## 流程

1. **先复述理解**：用 1-3 句说出我理解的"要做什么、给谁用、为什么现在做"，让用户低成本纠正。
2. **逐层提问（每轮 ≤ 3 个问题，按重要度排序）**：
   - 语义层：X 具体指什么？包含什么、不包含什么？（挖出非目标）
   - 价值层：成功长什么样？怎么验收？（挖出验收标准）
   - 约束层：数据从哪来？平台/性能/成本/语言？是否必须兼容旧行为？
   - 风险层：最不确定的假设是什么？哪条假设错了需求就变？
3. **给默认答案**：每个问题附"默认我会……，对吗？"，让用户选"对 / 改"而不是从零答。
4. **能推断的不问**：项目既有约定（`.agents/AGENTS.md` / `wotb-sync.md` / `DEVELOPER_GUIDE` / `docs/current-plan.md` 现有计划）直接用，不问。
5. **输出《需求确认单》并写入 `docs/current-plan.md`**（作为计划文件的业务目标/范围/验收标准基础），逐项写清：
   - 目标（一句话）
   - 范围 / 非目标
   - 验收标准（可测、可演示）
   - 关键假设
   - 待确认项（区分"阻塞性"与"可默认"）
6. **交接**：需求确认后转 `grill-with-docs`（实现角度）→ Plan → 用户批准 → 开发。

## 规则

- 每轮最多 3 个问题；问题越具体越好，禁止开放式问题轰炸。
- 只有阻塞性问题（影响范围或方案根本分歧）才停下等答复；非阻塞的用默认假设推进并标注"默认"。
- 不评价需求好坏，只澄清边界与可验收性。
- 最终必须落到书面《需求确认单》，不允许"口头懂了就开写"。
