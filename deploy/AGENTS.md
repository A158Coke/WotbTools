# deploy/ — 部署与生产指令

> 仓库级硬约定见 `.agents/AGENTS.md`；运维细节见 `docs/operations/observability.md` 与 `docs/auth/wargaming-asia-deployment.md`。

## 镜像与产物（经 deploy.yml / Dockerfile×3 核对）

- **registry 归属按 workload 划分**。TX workload（backend、frontend、keycloak）每次 Build **只构建一次**，由 BuildKit registry exporter（`docker/build-push-action` 的 `push: true`）**直传 Tencent TCR**：`<vars.TCR_REGISTRY>/<vars.TCR_NAMESPACE>/wotbtools-<component>:sha-<12>`。它们**不发布 GHCR、不导出 OCI archive、不经 rsync/SSH 传输、不在 TX 上 `docker load`、不调用 `deploy/tx/publish-loaded-image-to-tcr.sh`**；Build 不 SSH 到 TX，TX 只是 runtime host。Yecao workload（parser-worker、MinIO）保持既有 GHCR 路径不变（`ghcr.io/a158coke/wotbtools-<component>` 的 `sha-<12>` 与 `latest`），Build 不为它们登录 TCR。**Release identity 仍然只有不可变 tag `sha-<12>`，没有第二个 identity 概念**：不存在 image id、config digest、OCI archive identity 或 archive SHA256 比对。发布完整性证据是 registry 原生 manifest 回读——每个 TX component 在 push 后立即执行 `docker buildx imagetools inspect --format '{{.Manifest.Digest}}'`，要求返回值等于 BuildKit `steps.build.outputs.digest` 且形状为 `sha256:<64 hex>`；tag 缺失、digest 不一致或形状非法即 fail-closed，**绝不回退到 GHCR/OCI/rsync 传输**，也不推进任何可变 tag。TX workload 不再发布 `latest`（生产 Deploy 只解析 immutable `sha-<12>`，`deploy/tx/deploy.sh` 对可变或未解析引用一律拒绝，额外 tag 只会多出第二条命名契约）。凭据沿用既有 `vars.TCR_REGISTRY` / `vars.TCR_NAMESPACE` 与 `secrets.TCR_USERNAME` / `secrets.TCR_PASSWORD`，**只出现在三个 TX builder job**（job 内先断言 registry 是 `*.tencentyun.com` 且 `TCR_NAMESPACE` 非空，避免把凭据发往其它 registry），不新增第二套凭据，也绝不打印凭据。TCR 发布刻意**不做重试**：benchmark（run `35718721405` / job `106716287023`，build 277s、TCR push 1714s、manifest 校验 3s、`TCR_PUBLICATION=PASS`）证明一次不中断的直传即可成功；失败即 fail Build 并阻止该 release 部署，后续若出现真实瞬态失败再以独立证据引入有界重试（Phase 13）。已删除的旧传输机制：`scripts/ci/transfer-oci-to-tx.sh`、`scripts/ci/setup-tx-ssh.sh`、`scripts/ci/test-transfer-oci-to-tx.sh`、`deploy/test-tx-publication-helper.sh` 与 `.github/workflows/benchmark-tcr.yml`（没有任何调用方；benchmark 已被正常 Build 的直传取代）。`deploy/tx/publish-loaded-image-to-tcr.sh` **保留**为 TX host 上的手工 republish 运行手册工具，但 Build 与 Deploy 都不再调用它。`latest` 仍不是 deploy identity。**TCR 是 TX runtime image source**；TX 不拉取 GHCR，GHCR 与 TCR 凭据都不经 SSH、Compose、metadata 或 application environment 传递。
- TX 业务运行时是 `deploy/tx/docker-compose.yml` 的 `business-api`：同一 `wotbtools-backend` 镜像承载业务 API + 分布式回放控制面（PostgreSQL 是唯一 replay job authority，无后端选择器），**不发布任何端口**，只被 TX-internal frontend/Caddy/health-probe 访问（app :8087 `/api/health` + management :8088 `/actuator/health`）；凭据按服务分组 fail-closed，`KEYCLOAK_ADMIN_SERVER_URL` 固定 TX-internal `http://keycloak:8080`。**公开 API 路由已在 TX 内部终结**：frontend nginx upstream 固定 `http://business-api:8087`，`TX_BACKEND_UPSTREAM` 只接受这个 TX-internal 值（公网 host 与已退役的 Yecao `10.20.0.2:8087` 一律 fail-closed），且没有任何服务发布 8087；`deploy/tx/deploy.sh` 的 `assert_routing_boundary`（promote 之前）与只读门禁的 `tx-internal-api-route` / `distributed-execution-plane` token 双重断言。release plan 把 backend 镜像路由到 `business-api`（target `tx`）；Yecao 侧的 `wotb-backend`/`wotb-frontend`/`keycloak`/`postgres` 已随退役 PR 从 Compose、`deploy.sh` 白名单与 release plan 中删除，不再存在任何退役期选择器。改这些编排变量必须同步 `.env.example`、`docs/DEVELOPER_GUIDE.md`、`docs/auth/keycloak-tx-bootstrap.md` 与 `deploy/test-tx-runtime-config.sh`。TX 服务选择器含显式 `caddy`：Caddy-only（`WOTB_DEPLOY_SERVICES=caddy`、`WOTB_DEPLOY_IMAGE_SERVICES=`）只 reconcile Caddy——不拉取、不重建任何应用镜像服务，也不要求它们的 immutable identity：本次**不启动**的服务按实际生效的 identity 渲染（release metadata → live Compose document → 该 Compose service 的运行中容器，只接受 `sha-<12>` immutable tag），绝不被赋予本次 release 的 `TAG`（否则会把从未部署的服务的 identity 前进到新版本）；该 host 持有该服务部署状态（metadata / live Compose 具体引用 / 运行中容器）而三个来源都给不出合法 immutable identity 时 fail-closed 并指名服务；仅当该服务在本机从未部署过（PostgreSQL/broker bootstrap）才保留 incoming 声明，既不伪造 identity、也不回退到本次 `TAG`、也不写 metadata。启动判据由 `starts_image_service` 统一定义（`apply_services` 复用同一谓词），Caddy 被重建后由 `docker compose exec -T wotb-frontend nginx -t` + `nginx -s reload` 在运行容器内就地重新解析 `set_real_ip_from caddy`；只有真正启动应用镜像服务的选择器（`all`/`keycloak`/`wotb-frontend`/`business-api`）才要求该服务已记录/可推导的 immutable identity 并保持 fail-closed。
- **Build / Deploy 分离**：`.github/workflows/build.yml` 在 main 的应用或运行时 observability 变更后构建 component-local 的 immutable `sha-<12>` 镜像 tag，也支持 `workflow_dispatch` 单独构建 `backend` / `frontend` / `keycloak` / `all`；`changes` job 只解析一次事件携带的 full commit SHA，三个 builder checkout 同一个冻结 SHA，禁止 feature ref 或移动的 main 写入自动 production manifest，手工 Build 还必须验证 commit 已在 `origin/main` 历史中。纯 `deploy/observability/grafana/dashboards/**` 由 Grafana OpenTofu 管理，不触发应用 Build。成功的 main Build 通过 `workflow_run` 自动接力 `.github/workflows/deploy.yml`；Deploy 只消费对应 Build 的 immutable manifest，按 manifest 只更新受影响 service。生产事故操作进入仅手工触发的 `Ops Recovery`，不得把可变 `latest` 用于生产恢复。代码质量验证由 PR CI（merge gate）承担，Build/Deploy 不重复运行测试套件。生产 Compose 配置变化视为全部 runtime service 受影响；普通 targeted deploy 不重启其它应用 service。
- **PR 快速上线**：计划已明确且用户要求直接上线时，完成实现后直接提交、推送并开 PR，由 PR CI 验证；本地测试不是推送前阻塞条件。部署脚本仍必须保留静态配置校验、`verify-observability.sh` 数据链路 gate、失败诊断与无自动恢复路径。
- 生产编排 `deploy/docker-compose.prod.yml` + `deploy/deploy.sh`（fail-fast 校验）：Yecao 侧只声明 `parser-worker` 与观测栈（node-exporter/prometheus/loki/alloy/grafana），**不发布任何端口**；退役的业务应用（backend/frontend/Keycloak/business PostgreSQL）与 `health-probe` 客户端已删除，服务白名单里也没有它们。选中 parser-worker 时 fail-closed 拒绝给它数据库凭据/本地 job 目录/执行面开关，worker 必须无状态，唯一阻塞门禁是**容器存活**。业务后端的超时链契约（`AI_REVIEW_WORKER_OVERALL_DEADLINE_SEC=1100` 等）现在只由 TX 编排、`AiTimeoutChainContractTest`、`deploy/test-tx-runtime-config.sh` 与仓库根 `.env.example` 承担。
- **切 DNS 前的全业务 E2E 门禁**：`deploy/tx/pre-cutover-check.sh` 用 `wotbtools-e2e` 机器身份（client_credentials，唯一 realm role `wotbtools-user`，secret = `KEYCLOAK_E2E_CLIENT_SECRET`）驱动真实链路并逐项输出 PASS/FAIL token（`processing-e2e` / `dataset-result` / `map-overview` / `battle-playback-v2` / `minio` / `ai-facts` / `export` / `hof-replay-storage` / `parser-worker` / `admin-authz` / `business-data-integrity` 等）；公网边缘分两阶段：切 DNS 前 `public-edge-sni-*` 只证明 TX:443 可达且出示证书（`curl` 60 为预期通过），切 DNS 后 `--post-cutover` 强制 `public-tls-*`（受信任证书 + 解析到 TX + 2xx），全程不使用 `-k`。任一 FAIL 即 `PRE_CUTOVER_NOT_READY` / `POST_CUTOVER_NOT_READY`。门禁不做付费 AI 调用、对基础设施与用户数据只读，唯一写入是 TTL 自动回收的瞬时 job。回放 fixture 由 Deploy staged 到 `/opt/wotb-tx/e2e`（health-probe 只读挂载 `/e2e`）；Caddy 没有固定容器地址，readiness 走 `http://caddy/_wotb/...`，frontend 信任 `wotb_tx_internal` 子网。改这些 token、身份或输入必须同步 `docs/auth/keycloak-tx-bootstrap.md`、`docs/operations/rabbitmq.md`（DLQ 处置）、`.env.example`、`deploy/test-pre-cutover-check.sh` 与 `deploy/test-tx-runtime-config.sh`。
- MinIO 是独立的 `deploy/docker-compose.minio.yml` + `deploy/minio-deploy.sh`：只能由现有 Deploy workflow 的显式 `target=minio` 选择；不得加入普通 Yecao Compose 或自动发布路径。API 固定 `10.20.0.2:9000`（TX 控制面经 WireGuard 的端点）、Console 固定 `127.0.0.1:9001`；与 MinIO 同处 `wotb_internal` 的 Yecao parser-worker 不走这个地址，而是用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），两条端点分属不同 ownership、不得合并；Yecao provider mirror 缺失必须 fail-closed，详情见 `docs/operations/minio.md`。OpenTofu 管理两个同前缀同权限的应用身份（`worker` = Yecao parser-worker、`control_api` = TX 回放控制面，均只限 `temp/jobs/*`），身份分离只用于凭据隔离与单独轮换；HoF 回放原件不进 MinIO。
- RabbitMQ 是独立 TX runtime：Compose 仅管理 `rabbitmq:4.3.6-management-alpine`、volume、`10.20.0.1:5672` 与 `127.0.0.1:15672`；`infra/tofu/rabbitmq` 是唯一静态 topology owner，管理 vhost/users/permissions 与 `wotb.jobs` exchange、`wotb.parser`/`wotb.parser.retry`/`wotb.parser.dlq`/`wotb.parser.result` queues、bindings（应用不得在启动时重复声明同一拓扑，否则 `PRECONDITION_FAILED`）。结果回流方向为 worker → `parser.result`/`parser.failed` → `wotb.parser.result` → control-api，nack(requeue=false) 经 DLX `parser.dead` 进同一 DLQ；`control-api` 的 read 仅覆盖该结果队列（`^wotb\.parser\.result$`），不得再放宽。TX provider 必须使用 loopback Management API 与 `/opt/wotb-tx/tofu-provider-mirror`；RabbitMQ deploy 在 `tofu init` 前从 committed lockfile 推导精确 `linux_amd64` provider，先下载进 mirror 同文件系统的 staging 目录、只在校验 source/version/metadata/archive SHA256/lockfile `zh:` 全部通过后才 promote 到 canonical provider 目录（`tofu providers mirror` 绝不直接写生产目录，失败不写 marker、不进入 init），损坏或不完整的 exact-version canonical 包由下一次 staged bootstrap 自动修复而其他版本/多个 archive 仍 fail-closed，正式 init 仍禁止 direct registry fallback，下载、版本或 checksum 异常全部 fail-closed。RabbitMQ-only deploy 不启动 Keycloak/PostgreSQL/frontend，详见 `docs/operations/rabbitmq.md`。
- Yecao parser-worker 是**显式选中**的执行面服务（`deploy/docker-compose.prod.yml` 的 `parser-worker`，镜像 `ghcr.io/a158coke/wotbtools-parser-worker`，`docker/Dockerfile.parser-worker`）：无公网端口、无数据库凭据，只消费 TX broker 并读写 Yecao MinIO；`deploy/deploy.sh` 把它纳入白名单、镜像 tag 重写与 metadata，选中时 fail-closed 要求 `TX_RABBITMQ_PARSER_WORKER_PASSWORD` / `YECAO_MINIO_WORKER_ACCESS_KEY` / `YECAO_MINIO_WORKER_SECRET_KEY`，并以**容器存活 gate**（无 HTTP 端点）判定部署成功、失败即停止该服务防 runaway restart。它**是 Yecao 宿主上唯一的应用服务**（`all` 选择器已随退役删除），因此观测-only 部署不需要新凭据；MinIO 端点归 worker 自己的 topology——它与 MinIO 同处 `wotb_internal`，用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），绝不复用控制面经 WireGuard 的 `YECAO_MINIO_ENDPOINT=10.20.0.2:9000`（容器 → 宿主 → published-port 的 hairpin 不可达，正是 `PARSER_WORKER_STORAGE_UNAVAILABLE` 的成因）；改 worker 的编排变量必须同步 `.env.example`、`docs/operations/parser-worker.md` 与 `deploy/test-deploy-contract.sh`。
- 反向代理 `deploy/nginx/nginx.conf`：`/api/replay/analyze` 固定 `proxy_read/send_timeout 1120s` + `proxy_buffering off`（SSE 流式）；其余 120s。
- **SPA 缓存策略（frontend 部署即生效的关键）**：`location = /index.html` 固定 `Cache-Control: no-cache, no-store, must-revalidate`（禁止浏览器缓存入口页，新 bundle hash 部署后立即生效）；`location /assets/`（Vite 内容 hash 产物）固定 `Cache-Control: public, max-age=31536000, immutable`，且 404 不 fallback 到 index.html。改缓存头会影响用户能否看到新前端版本，改动需在 `?view=hof-admin` 等页验证。
- **Build identity（防猜版本）**：Build 的 `changes` job 只在 `main` 上解析一次 full commit SHA，并由 backend/frontend/keycloak 三个 job checkout 同一个 SHA；三个镜像均注入该 SHA 的 `BUILD_COMMIT` build-arg。Backend 的 `StartupReleaseDiagnostics` 在启动时输出 full build commit、对应的 `sha-<12>` immutable image tag 与 Flyway migration ceiling；Frontend 的 `vite.config.js` 据此生成 `dist/version.json`（`buildCommit`）并在启动 console 输出 `[build] commit=... time=...`；Keycloak 通过 `WOTBTOOLS_BUILD_COMMIT` 在启动时输出 `WotBTools Keycloak build=...`（Docker 上下文无 `.git`，必须经 build-arg 注入，本地前端构建才 fallback `git rev-parse`）。生产异常时先核对三个运行服务的 release diagnostics 与 immutable image identity。
- 本地完整 Docker Compose 开发环境已退役；Keycloak realm 集成验证仅使用 `deploy/test-keycloak-tofu.sh` 的 disposable PostgreSQL、Keycloak 与 local OpenTofu state。

## 运维（安全）

- 备份：`postgres-backup.sh`/`postgres-restore.sh`/`postgres-backup-inspect.sh`（本地保留）；`database-backup.yml` 独立运行；normal Deploy 不调用 backup，也不把现有本地备份描述为 COS 完成。COS bucket、prefix、CLI/兼容接口、凭据与 retention 属于后续独立 PR，不能猜测或复用 artifact bucket。**已知缺口（NO-TOUCH，登记为 Production Data Protection Review finding）**：这三个脚本以 Yecao 宿主 `docker compose ... postgres` 为目标，而该 service 已随 legacy application runtime 退役删除（`init-db.sql` 一并删除），脚本本身按退役 PR 的 NO-TOUCH 规则不修改——在备份目标重新设计前它们无法再对任何现存数据库执行。
- 观测：`deploy/observability/`（Alloy config + Grafana dashboards/provisioning）；指标名被 dashboards 引用，改名需同步 JSON。Grafana dashboard API ownership 由 `infra/tofu/grafana` 管理，PR plan 后 main merge 自动 apply，Prometheus/Loki datasource 仍由 file provisioning 管理。Prometheus 必须验证 backend、node-exporter、Prometheus、Loki、Grafana 五类 target 为 `up == 1`；Grafana 必须验证 health、Prometheus/Loki datasource health、全部 dashboard UID API 与 Production Overview 默认首页。Keycloak 不再进入 Prometheus metrics contract，登录/IdP/callback 通过 Alloy → Loki 日志验证。**退役窗口说明**：Yecao 宿主已不再运行 backend/Keycloak/frontend 容器，因此 `up == 1` 的 target 集合、`verify-observability.sh` 的执行容器与 `monitor.wotbtools.com` 的公网服务路径需要 observability realignment PR 重新对齐；在那之前 Yecao 部署会持续输出 `OBSERVABILITY DEGRADED`（非阻塞）。生产上线后的 metrics endpoint、Prometheus target/query、Loki backend/Keycloak/frontend canary stream 由 `deploy/verify-observability.sh` 串行验证；CI 用 `deploy/test-observability-e2e.sh` 验证真实 Docker emitter → 生产 Alloy → Loki 的三条 ownership path，并用 `deploy/test-grafana-runtime.sh` 验证 datasource provisioning 与 dashboard API adoption。
- 生产发布必须先由 Actions 上传到 `/opt/wotb/deploy.incoming`，在 incoming project root 中完成 compose config/pull，再以同文件系统目录 promote 到 `/opt/wotb/deploy`；application gate 只对 Yecao 侧的 `parser-worker` 做**容器存活**判定（该服务无 HTTP 端点，`health-probe` 客户端已随退役删除）；业务 API 的 HTTP 健康探测、Keycloak OIDC discovery 与数据库连通性检查由 TX 侧 `deploy/tx/deploy.sh` 承担。失败诊断必须保留 release/affected/image/status/log 信息，并停止确认失败的 affected service，防止 runaway restart；不自动恢复旧 application image。成功应用发布才原子更新 `/opt/wotb/production-release.json`（0600）；其它 service metadata 不变。Prometheus/Loki/Alloy/Grafana 失败只能输出 `OBSERVABILITY DEGRADED`，不得使健康应用恢复或回退。Yecao 侧不再有一次性应用恢复入口：`Ops Recovery` workflow、`ops-recovery.sh` 与 `test-ops-recovery.sh` 已随退役删除（其目标 backend/frontend/keycloak 与 `VPS_HOST` 都只服务退役面）；受影响的业务服务按 TX 路径重新发布。禁止对 live `deploy/` 直接 SCP 覆盖，也禁止只发送 HUP 作为 Grafana/观测配置生效保证。
- 生产发布在 staged compose pull 后、live promote 前必须运行 `validate-alloy-config.sh`；Alloy Android 下载 `stage.match` selector 使用 LogQL 安全的 `[.]`，禁止回退到会触发 `invalid char escape` 的 `\\.` 写法。
- Grafana 生产 API 校验必须复用 `deploy/grafana-api-request.sh` 这条生产 backend Alpine 运行时可用的 BusyBox `wget` 路径：调用方只传 `/api/...`，helper 在 backend 容器内唯一拼接 Grafana hostname 并生成 `Authorization: Basic` header（不得把密码放 URL、命令输出或日志），datasource health 的唯一成功值是 JSON `status=OK`。CI runtime smoke 还必须在 Alpine 3.22 中验证正确凭据通过、错误凭据失败，以防回退到 GNU-only `wget` 参数或 double URL prefix。
- Loki canary 校验在 emitter 启动前固定 `start`，重试时只推进 `end`；响应必须是 `status=success`、至少一个 result stream、至少一个 values 样本并包含 marker。Keycloak canary 是加入 `wotb_internal` 网络的独立 Alpine emitter，只用于验证 Alloy 的 ownership 采集路径，不得把 Keycloak 镜像当 shell 执行。
- Keycloak 运行时契约由 `deploy/test-keycloak-runtime.sh` 独立验证：自定义镜像必须以 `start --optimized` 启动，保留 PostgreSQL 与应用 OIDC discovery；不再启用或暴露 management health/metrics 端口，且不得出现启动时 Quarkus augmentation。`.github/workflows/ci.yml` 的 `keycloak-runtime` 是该契约的真实 Docker gate。

## Gate boundary

- Blocking production health（Yecao）：`parser-worker` 容器存活（该服务无 HTTP 端点）。业务 API、frontend 与 Keycloak 的 HTTP/OIDC 探测属于 TX deploy（`deploy/tx/deploy.sh`）。
- Non-blocking observability：Prometheus、Loki、Alloy、Grafana、datasources、dashboards、metrics 与 log ingestion。
- `verify-observability.sh` 必须保持 fail-closed；deploy orchestration 负责把失败记录为 degraded，而不是用 `|| true` 改写 verifier 语义。
- 排障：SSH VPS `ssh -i "$env:USERPROFILE\.ssh\wotb_vps_deploy" -o IdentitiesOnly=yes root@45.136.14.101 -p 58361`，`docker logs wotb-parser-worker-1 --tail 100`——Yecao 宿主只运行 parser-worker 与观测服务，业务后端日志在 TX；也可运行仅 `workflow_dispatch` 的 `.github/workflows/prod-diagnostics.yml` 只读采集同一批日志。常见根因：凭据缺失导致的 crash loop、broker/MinIO 端点不可达。
- secret 一律 GitHub Secrets / Variables → SSH 运行时 env（仓库根 `.env.example` 只列变量名）；TX 不维护本地 secret env 文件，禁止落库或写死。赞助/收款信息不硬编码进页面或仓库（运行时只读挂载）。
