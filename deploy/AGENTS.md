# deploy/ — 部署与生产指令

> 仓库级硬约定见 `.agents/AGENTS.md`；运维细节见 `docs/operations/observability.md` 与 `docs/auth/wargaming-asia-deployment.md`。

## 镜像与产物（经 deploy.yml / Dockerfile×3 核对）

- **镜像身份**：单一 `.github/workflows/release.yml` 解释完整 push range 并调用 reusable Build/Deploy/Tofu Apply。Build 只构建 business-api/frontend/keycloak/parser-worker/minio 五个 component 中受影响者，发布 TCR/GHCR 正确归属下的 immutable `sha-<12>`，输出 digest；Deploy 传递精确 Build 身份，config-only 从 v2 metadata 读取现有身份。TX 镜像 registry prefix 必须从 `vars.TCR_REGISTRY/TCR_NAMESPACE` 传入 host，不可依赖默认 namespace。
- TX 业务运行时是 `deploy/tx/docker-compose.yml` 的 `business-api`：镜像为 `wotbtools-business-api`，承载业务 API + 分布式回放控制面（PostgreSQL 是唯一 replay job authority，无后端选择器），不发布任何端口；只被 TX-internal frontend/Caddy/health-probe 访问（app :8087 `/api/health` + management :8088 `/actuator/health`）。
- **单一发布闭环**：PR 的 `CI / Required Gate` 是唯一代码验证门禁；main push 的 Release 按受影响服务/root 拆成独立 lane，支持部分成功。Build、Deploy、Tofu Apply 各支持 reusable 调用与单目标手动入口，不再有 Build `workflow_run` 链、旧 deployment-manifest 或 all selector。部署配置与应用 metadata v2 更新必须 fail-closed，成功服务独立记录，失败不自动回滚。
- **PR 快速上线**：计划已明确且用户要求直接上线时，完成实现后直接提交、推送并开 PR，由 PR CI 验证；本地测试不是推送前阻塞条件。部署脚本仍必须保留静态配置校验、`verify-observability.sh` 数据链路 gate、失败诊断与无自动恢复路径。
- 生产编排 `deploy/docker-compose.prod.yml` + `deploy/deploy.sh`（fail-fast 校验）：Yecao 侧只声明 `parser-worker` 与观测栈（node-exporter/prometheus/loki/alloy/grafana），**不发布任何端口**；退役的业务应用（backend/frontend/Keycloak/business PostgreSQL）与 `health-probe` 客户端已删除，服务白名单里也没有它们。选中 parser-worker 时 fail-closed 拒绝给它数据库凭据/本地 job 目录/执行面开关，worker 必须无状态，唯一阻塞门禁是**容器存活**。业务后端的超时链契约（`AI_REVIEW_WORKER_OVERALL_DEADLINE_SEC=1100` 等）现在只由 TX 编排、`AiTimeoutChainContractTest`、`deploy/test-tx-runtime-config.sh` 与仓库根 `.env.example` 承担。
- **全业务运行时 E2E 检查**：`deploy/tx/runtime-check.sh` 用 `wotbtools-e2e` 机器身份（client_credentials，唯一 realm role `wotbtools-user`，secret = `KEYCLOAK_E2E_CLIENT_SECRET`）驱动真实链路并逐项输出 PASS/FAIL token（`processing-e2e` / `dataset-result` / `map-overview` / `battle-playback-v2` / `minio` / `ai-facts` / `export` / `hof-replay-storage` / `parser-worker` / `admin-authz` 等；公网边缘只接受受信任 TLS：`public-tls-web` / `public-tls-auth` 必须由 `WOTB_E2E_PUBLIC_IP`（TX 地址）应答、出示受信任证书且 HTTP 2xx，`curl` 60（链尚未受信）一律 FAIL，全程不使用 `-k`。任一 FAIL 即 `TX_RUNTIME_NOT_READY`。检查不做付费 AI 调用、对基础设施与用户数据只读，唯一写入是 TTL 自动回收的瞬时 job。回放 fixture 由 Deploy staged 到 `/opt/wotb-tx/e2e`（health-probe 只读挂载 `/e2e`）；Caddy 没有固定容器地址，readiness 走 `http://caddy/_wotb/...`，frontend 信任 `wotb_tx_internal` 子网。改这些 token、身份或输入必须同步 `docs/auth/keycloak-tx-bootstrap.md`、`docs/operations/rabbitmq.md`（DLQ 处置）、`.env.example`、`deploy/test-tx-runtime-check.sh` 与 `deploy/test-tx-runtime-config.sh`。
- MinIO 是独立的 `deploy/docker-compose.minio.yml` + `deploy/minio-deploy.sh`：只能由现有 Deploy workflow 的显式 `service=minio` 选择；不得加入普通 Yecao Compose 或自动发布路径。API 固定 `10.20.0.2:9000`（TX 控制面经 WireGuard 的端点）、Console 固定 `127.0.0.1:9001`；与 MinIO 同处 `wotb_internal` 的 Yecao parser-worker 不走这个地址，而是用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），两条端点分属不同 ownership、不得合并；Yecao provider mirror 缺失必须 fail-closed，详情见 `docs/operations/minio.md`。OpenTofu 管理两个同前缀同权限的应用身份（`worker` = Yecao parser-worker、`control_api` = TX 回放控制面，均只限 `temp/jobs/*`），身份分离只用于凭据隔离与单独轮换；HoF 回放原件不进 MinIO。
- RabbitMQ 是独立 TX runtime：Compose 仅管理 `rabbitmq:4.3.6-management-alpine`、volume、`10.20.0.1:5672` 与 `127.0.0.1:15672`；`infra/tofu/rabbitmq` 是唯一静态 topology owner，管理 vhost/users/permissions 与 `wotb.jobs` exchange、`wotb.parser`/`wotb.parser.retry`/`wotb.parser.dlq`/`wotb.parser.result` queues、bindings（应用不得在启动时重复声明同一拓扑，否则 `PRECONDITION_FAILED`）。结果回流方向为 worker → `parser.result`/`parser.failed` → `wotb.parser.result` → control-api，nack(requeue=false) 经 DLX `parser.dead` 进同一 DLQ；`control-api` 的 read 仅覆盖该结果队列（`^wotb\.parser\.result$`），不得再放宽。TX provider 必须使用 loopback Management API 与 `/opt/wotb-tx/tofu-provider-mirror`；RabbitMQ deploy 在 `tofu init` 前从 committed lockfile 推导精确 `linux_amd64` provider，先下载进 mirror 同文件系统的 staging 目录、只在校验 source/version/metadata/archive SHA256/lockfile `zh:` 全部通过后才 promote 到 canonical provider 目录（`tofu providers mirror` 绝不直接写生产目录，失败不写 marker、不进入 init），损坏或不完整的 exact-version canonical 包由下一次 staged bootstrap 自动修复而其他版本/多个 archive 仍 fail-closed，正式 init 仍禁止 direct registry fallback，下载、版本或 checksum 异常全部 fail-closed。RabbitMQ-only deploy 不启动 Keycloak/PostgreSQL/frontend，详见 `docs/operations/rabbitmq.md`。
- Yecao parser-worker 是**显式选中**的执行面服务（`deploy/docker-compose.prod.yml` 的 `parser-worker`，镜像 `ghcr.io/a158coke/wotbtools-parser-worker`，`docker/Dockerfile.parser-worker`）：无公网端口、无数据库凭据，只消费 TX broker 并读写 Yecao MinIO；`deploy/deploy.sh` 把它纳入白名单、镜像 tag 重写与 metadata，选中时 fail-closed 要求 `TX_RABBITMQ_PARSER_WORKER_PASSWORD` / `YECAO_MINIO_WORKER_ACCESS_KEY` / `YECAO_MINIO_WORKER_SECRET_KEY`，并以**容器存活 gate**（无 HTTP 端点）判定部署成功、失败即停止该服务防 runaway restart。它**是 Yecao 宿主上唯一的应用服务**（`all` 选择器已随退役删除），因此观测-only 部署不需要新凭据；MinIO 端点归 worker 自己的 topology——它与 MinIO 同处 `wotb_internal`，用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），绝不复用控制面经 WireGuard 的 `YECAO_MINIO_ENDPOINT=10.20.0.2:9000`（容器 → 宿主 → published-port 的 hairpin 不可达，正是 `PARSER_WORKER_STORAGE_UNAVAILABLE` 的成因）；改 worker 的编排变量必须同步 `.env.example`、`docs/operations/parser-worker.md` 与 `deploy/test-deploy-contract.sh`。
- 反向代理 `deploy/nginx/nginx.conf`：`/api/replay/analyze` 固定 `proxy_read/send_timeout 1120s` + `proxy_buffering off`（SSE 流式）；其余 120s。
- **SPA 缓存策略（frontend 部署即生效的关键）**：`location = /index.html` 固定 `Cache-Control: no-cache, no-store, must-revalidate`（禁止浏览器缓存入口页，新 bundle hash 部署后立即生效）；`location /assets/`（Vite 内容 hash 产物）固定 `Cache-Control: public, max-age=31536000, immutable`，且 404 不 fallback 到 index.html。改缓存头会影响用户能否看到新前端版本，改动需在 `?view=hof-admin` 等页验证。
- **Build identity**：Build checkout 完整冻结 source SHA，并由 Build output 提供完整 image ref、immutable tag、source SHA 和 digest。TX 三镜像直传 TCR；Yecao parser-worker/MinIO 只用 GHCR。business-api 镜像产物名为 `wotbtools-business-api`，内部 Maven module 仍叫 `wotb-web`。
- 本地完整 Docker Compose 开发环境已退役；Keycloak realm 集成验证仅使用 `deploy/test-keycloak-tofu.sh` 的 disposable PostgreSQL、Keycloak 与 local OpenTofu state。

## 运维（安全）

- 备份：`postgres-backup.sh`/`postgres-restore.sh`/`postgres-backup-inspect.sh`（本地保留）；`database-backup.yml` 独立运行；normal Deploy 不调用 backup，也不把现有本地备份描述为 COS 完成。COS bucket、prefix、CLI/兼容接口、凭据与 retention 属于后续独立 PR，不能猜测或复用 artifact bucket。**已知缺口（NO-TOUCH，登记为 Production Data Protection Review finding）**：这三个脚本以 Yecao 宿主 `docker compose ... postgres` 为目标，而该 service 已随 legacy application runtime 退役删除（`init-db.sql` 一并删除），脚本本身按退役 PR 的 NO-TOUCH 规则不修改——在备份目标重新设计前它们无法再对任何现存数据库执行。
- 观测：`deploy/observability/`（Alloy config + Grafana dashboards/provisioning）；指标名被 dashboards 引用，改名需同步 JSON。Grafana dashboard API ownership 由 `infra/tofu/grafana` 管理，PR plan 后 main merge 自动 apply，Prometheus/Loki datasource 仍由 file provisioning 管理。Prometheus 必须验证 backend、node-exporter、Prometheus、Loki、Grafana 五类 target 为 `up == 1`；Grafana 必须验证 health、Prometheus/Loki datasource health、全部 dashboard UID API 与 Production Overview 默认首页。Keycloak 不再进入 Prometheus metrics contract，登录/IdP/callback 通过 Alloy → Loki 日志验证。**退役窗口说明**：Yecao 宿主已不再运行 backend/Keycloak/frontend 容器，因此 `up == 1` 的 target 集合、`verify-observability.sh` 的执行容器与 `monitor.wotbtools.com` 的公网服务路径需要 observability realignment PR 重新对齐；在那之前 Yecao 部署会持续输出 `OBSERVABILITY DEGRADED`（非阻塞）。生产上线后的 metrics endpoint、Prometheus target/query、Loki backend/Keycloak/frontend canary stream 由 `deploy/verify-observability.sh` 串行验证；CI 用 `deploy/test-observability-e2e.sh` 验证真实 Docker emitter → 生产 Alloy → Loki 的三条 ownership path，并用 `deploy/test-grafana-runtime.sh` 验证 datasource provisioning 与 dashboard API adoption。
- 生产 Deploy 逐个 service staging、校验配置/目标镜像并执行 readiness；TX metadata 路径 `/opt/wotb-tx/production-release.json` 只记录 business-api/frontend/keycloak，Yecao `/opt/wotb/production-release.json` 只记录 parser-worker/minio，均 schemaVersion 2、原子写、0600。config-only 成功只推进 configSha，镜像身份不变；固定上游服务不写入应用 metadata。失败不推进该服务 metadata，不自动恢复旧镜像。Yecao 观测失败只输出 `OBSERVABILITY DEGRADED`。
- 生产发布在 staged compose pull 后、live promote 前必须运行 `validate-alloy-config.sh`；Alloy Android 下载 `stage.match` selector 使用 LogQL 安全的 `[.]`，禁止回退到会触发 `invalid char escape` 的 `\\.` 写法。
- Grafana 生产 API 校验必须复用 `deploy/grafana-api-request.sh` 这条生产 backend Alpine 运行时可用的 BusyBox `wget` 路径：调用方只传 `/api/...`，helper 在 backend 容器内唯一拼接 Grafana hostname 并生成 `Authorization: Basic` header（不得把密码放 URL、命令输出或日志），datasource health 的唯一成功值是 JSON `status=OK`。CI runtime smoke 还必须在 Alpine 3.22 中验证正确凭据通过、错误凭据失败，以防回退到 GNU-only `wget` 参数或 double URL prefix。
- Loki canary 校验在 emitter 启动前固定 `start`，重试时只推进 `end`；响应必须是 `status=success`、至少一个 result stream、至少一个 values 样本并包含 marker。Keycloak canary 是加入 `wotb_internal` 网络的独立 Alpine emitter，只用于验证 Alloy 的 ownership 采集路径，不得把 Keycloak 镜像当 shell 执行。
- Keycloak 运行时契约由 `deploy/test-keycloak-runtime.sh` 独立验证：自定义镜像必须以 `start --optimized` 启动，保留 PostgreSQL 与应用 OIDC discovery；不再启用或暴露 management health/metrics 端口，且不得出现启动时 Quarkus augmentation。`.github/workflows/ci.yml` 的 `keycloak-runtime` 是该契约的真实 Docker gate。

## Gate boundary

- Blocking production health（Yecao）：`parser-worker` 容器存活（该服务无 HTTP 端点）。业务 API、frontend 与 Keycloak 的 HTTP/OIDC 探测属于 TX deploy（`deploy/tx/deploy.sh`）。
- Non-blocking observability：Prometheus、Loki、Alloy、Grafana、datasources、dashboards、metrics 与 log ingestion。
- `verify-observability.sh` 必须保持 fail-closed；deploy orchestration 负责把失败记录为 degraded，而不是用 `|| true` 改写 verifier 语义。
- 排障：SSH VPS `ssh -i "$env:USERPROFILE\.ssh\wotb_vps_deploy" -o IdentitiesOnly=yes root@45.136.14.101 -p 58361`，`docker logs wotb-parser-worker-1 --tail 100`——Yecao 宿主只运行 parser-worker 与观测服务，业务后端日志在 TX；也可运行仅 `workflow_dispatch` 的 `.github/workflows/prod-diagnostics.yml` 只读采集同一批日志。常见根因：凭据缺失导致的 crash loop、broker/MinIO 端点不可达。
- secret 一律 GitHub Secrets / Variables → SSH 运行时 env（仓库根 `.env.example` 只列变量名）；TX 不维护本地 secret env 文件，禁止落库或写死。赞助/收款信息不硬编码进页面或仓库（运行时只读挂载）。
