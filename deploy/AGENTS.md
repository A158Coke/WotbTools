# deploy/ — 部署与生产指令

> 仓库级硬约定见 `.agents/AGENTS.md`；运维细节见 `docs/operations/observability.md` 与 `docs/auth/wargaming-asia-deployment.md`。

## 镜像与产物（服务 workflow + Dockerfile）

- **镜像身份**：应用发布都必须先冻结完整 source SHA，并保留不可变 SHA/tag + registry digest 供 provenance 与诊断。TX 的 `business-api` 与 `frontend` 是 digest-pinned 车道：GitHub 只确定 release source/输入，Gitee 作为国内源码传输，TX 从 exact SHA 构建并验证后发布到 TCR，生产 Compose 必须消费 `repo@sha256:<digest>`（分别由 `TX_BUSINESS_API_IMAGE_REF` / `TX_FRONTEND_IMAGE_REF` 提供），禁止回退 `latest`。其他尚未迁移的应用 owner 仍沿用各自现有 `latest`/freshness 契约。TX 镜像只用 TCR，Yecao 镜像只用 GHCR；TX registry prefix 必须从 `vars.TCR_REGISTRY/TCR_NAMESPACE` 传给 host，不可依赖默认 namespace。
- TX 业务运行时定义在 `deploy/tx/business-api.compose.yml`，由 `deploy/tx/docker-compose.yml` 汇总：镜像为 `wotbtools-business-api`，承载业务 API + 分布式回放控制面（PostgreSQL 是唯一 replay job authority，无后端选择器），仅将 management :8088 绑定到 WireGuard `10.20.0.1` 供 Yecao Prometheus 抓取；app :8087 只被 TX-internal frontend/Caddy/health-probe 访问。
- **独立发布闭环**：PR 的 `CI / Required Gate` 是唯一代码验证门禁；六个应用 owner 在每次 main push 运行，固定基础设施按各自路径触发，手动入口只作用于所属服务。不要新增跨服务 planner、reusable Build/Deploy/Tofu DAG、`workflow_run` 链、deployment manifest 或 all selector。应用按当前 main 部署，持久状态校验必须 fail-closed，失败不自动回滚。
- **PR 快速上线**：计划已明确且用户要求直接上线时，完成实现后直接提交、推送并开 PR，由 PR CI 验证；本地测试不是推送前阻塞条件。部署脚本仍必须保留静态配置校验、`verify-observability.sh` 数据链路 gate、失败诊断与无自动恢复路径。
- 生产编排 `deploy/docker-compose.prod.yml` + `deploy/deploy.sh`（fail-fast 校验）：Yecao 侧声明 `parser-worker`、预部署的 `ai-service` 与观测栈（node-exporter/prometheus/loki/alloy/grafana），仅 Grafana `10.20.0.2:3000` 与 Loki `10.20.0.2:3100` 绑定 WireGuard；退役的业务应用（backend/frontend/Keycloak/business PostgreSQL）与 `health-probe` 客户端已删除，服务白名单里也没有它们。选中 parser-worker 时 fail-closed 拒绝给它数据库凭据/本地 job 目录/执行面开关；部署前由 `dependency-readiness.sh parser-worker` 从 consumer network 做 RabbitMQ 身份/队列被动检查与 MinIO 只读列表，部署后以**容器存活**为服务健康 gate。业务后端的超时链契约（`AI_REVIEW_WORKER_OVERALL_DEADLINE_SEC=1100` 等）已随 AI 配置一并归属 Yecao `ai-service`（`deploy/docker-compose.prod.yml`）与 `AiTimeoutChainContractTest`；TX 业务编排不再携带任何 AI provider 变量或 secret，只保留 `deploy/test-tx-runtime-config.sh` 校验的 `/api/ai/**` → `10.20.0.2:8089` ingress 路由。
- **全业务运行时 E2E 检查**：`deploy/tx/runtime-check.sh` 用 `wotbtools-e2e` 机器身份（client_credentials，唯一 realm role `wotbtools-user`，secret = `KEYCLOAK_E2E_CLIENT_SECRET`）驱动真实链路并逐项输出 PASS/FAIL token（`processing-e2e` / `dataset-result` / `map-overview` / `battle-playback-v2` / `minio` / `export` / `hof-replay-storage` / `parser-worker` / `admin-authz` 等；公网边缘只接受受信任 TLS：`public-tls-web` / `public-tls-auth` 必须由 `WOTB_E2E_PUBLIC_IP`（TX 地址）应答、出示受信任证书且 HTTP 2xx，`curl` 60（链尚未受信）一律 FAIL，全程不使用 `-k`。任一 FAIL 即 `TX_RUNTIME_NOT_READY`。检查不做付费 AI 调用、对基础设施与用户数据只读，唯一写入是 TTL 自动回收的瞬时 job。回放 fixture 由 Deploy staged 到 `/opt/wotb-tx/e2e`（health-probe 只读挂载 `/e2e`）；Caddy 没有固定容器地址，readiness 走 `http://caddy/_wotb/...`，frontend 信任 `wotb_tx_internal` 子网。改这些 token、身份或输入必须同步 `docs/auth/keycloak-tx-bootstrap.md`、`docs/operations/rabbitmq.md`（DLQ 处置）、`.env.example`、`deploy/test-tx-runtime-check.sh` 与 `deploy/test-tx-runtime-config.sh`。
- MinIO 是独立的 `.github/workflows/minio.yml` + `deploy/docker-compose.minio.yml` + `deploy/minio-deploy.sh`：每次 main push 都自动构建部署 `latest`，也保留显式 `workflow_dispatch`；不得加入普通 Yecao Compose 或 parser-worker 发布链。API 固定 `10.20.0.2:9000`（TX 控制面经 WireGuard 的端点）、Console 固定 `127.0.0.1:9001`；与 MinIO 同处 `wotb_internal` 的 Yecao parser-worker 不走这个地址，而是用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），两条端点分属不同 ownership、不得合并；Yecao provider mirror 缺失必须 fail-closed，详情见 `docs/operations/minio.md`。OpenTofu 管理两个同前缀同权限的应用身份（`worker` = Yecao parser-worker、`control_api` = TX 回放控制面，均只限 `temp/jobs/*`），身份分离只用于凭据隔离与单独轮换；HoF 回放原件不进 MinIO。
- RabbitMQ 是独立 TX runtime：Compose 仅管理 `rabbitmq:4.3.6-management-alpine`、volume、`10.20.0.1:5672` 与 `127.0.0.1:15672`；`infra/tofu/rabbitmq` 是唯一静态 topology owner，管理 vhost/users/permissions 与 `wotb.jobs` exchange、`wotb.parser`/`wotb.parser.retry`/`wotb.parser.dlq`/`wotb.parser.result` queues、bindings（应用不得在启动时重复声明同一拓扑，否则 `PRECONDITION_FAILED`）。结果回流方向为 worker → `parser.result`/`parser.failed` → `wotb.parser.result` → control-api，nack(requeue=false) 经 DLX `parser.dead` 进同一 DLQ；`control-api` 的 read 仅覆盖该结果队列（`^wotb\.parser\.result$`），不得再放宽。TX provider 必须使用 loopback Management API 与 `/opt/wotb-tx/tofu-provider-mirror`；RabbitMQ deploy 在 `tofu init` 前从 committed lockfile 推导精确 `linux_amd64` provider，先下载进 mirror 同文件系统的 staging 目录、只在校验 source/version/metadata/archive SHA256/lockfile `zh:` 全部通过后才 promote 到 canonical provider 目录（`tofu providers mirror` 绝不直接写生产目录，失败不写 marker、不进入 init），损坏或不完整的 exact-version canonical 包由下一次 staged bootstrap 自动修复而其他版本/多个 archive 仍 fail-closed，正式 init 仍禁止 direct registry fallback，下载、版本或 checksum 异常全部 fail-closed。RabbitMQ-only deploy 不启动 Keycloak/PostgreSQL/frontend，详见 `docs/operations/rabbitmq.md`。
- Yecao parser-worker 是**显式服务 owner**（`deploy/docker-compose.prod.yml` 的 `parser-worker`，镜像 `ghcr.io/a158coke/wotbtools-parser-worker`，`docker/Dockerfile.parser-worker`）：无公网端口、无数据库凭据，只消费 TX broker 并读写 Yecao MinIO；`deploy/deploy.sh` 把它纳入白名单、所属 `latest` 镜像，workflow 在 mutation 前要求 `TX_RABBITMQ_PARSER_WORKER_PASSWORD` / `YECAO_MINIO_WORKER_ACCESS_KEY` / `YECAO_MINIO_WORKER_SECRET_KEY`，并通过只读消费侧 readiness 验证 broker auth/vhost/queue 与 MinIO prefix listing；部署后以**容器存活 gate**判定服务健康，失败即停止该服务防 runaway restart。它**与预部署的 ai-service 一起运行在 Yecao 宿主**（`all` 选择器已随退役删除），因此观测-only workflow 不需要新凭据；MinIO 端点归 worker 自己的 topology——它与 MinIO 同处 `wotb_internal`，用 Docker 服务发现 `minio:9000`（`PARSER_WORKER_MINIO_ENDPOINT`），绝不复用控制面经 WireGuard 的 `YECAO_MINIO_ENDPOINT=10.20.0.2:9000`（容器 → 宿主 → published-port 的 hairpin 不可达，正是 `PARSER_WORKER_STORAGE_UNAVAILABLE` 的成因）；改 worker 的编排变量必须同步 `.env.example`、`docs/operations/parser-worker.md` 与 `deploy/test-deploy-contract.sh`。
- 反向代理：TX 线上边缘配置是 `deploy/tx/nginx/frontend.conf.template`（Caddy 终 TLS 后整站转 `wotb-frontend:80`，由 frontend 镜像的 nginx template entrypoint 渲染到 `/etc/nginx/conf.d/default.conf`）；`deploy/nginx/nginx.conf` 只是镜像内的烘焙副本，运行时被同路径覆盖，不得据它判断线上路由。`location ^~ /api/ai/` 反代到 `${AI_UPSTREAM}`（Yecao ai-service `10.20.0.2:8089`，仅 WireGuard，不重写 path：公开与 controller 路径都是 `/api/ai/...`），固定 `proxy_read/send_timeout 1120s` + `proxy_buffering off`（SSE）；旧 `/api/replay/analyze` 的专用 location 已随该端点退役一并移除（此类请求落回通用 `/api/`）；其余 `/api/` 120s。`TX_AI_UPSTREAM` 与 `TX_BACKEND_UPSTREAM` 一样在 `deploy/tx/deploy.sh` fail-closed。
- **SPA 缓存策略（frontend 部署即生效的关键）**：`location = /index.html` 固定 `Cache-Control: no-cache, no-store, must-revalidate`（禁止浏览器缓存入口页，新 bundle hash 部署后立即生效）；`location /assets/`（Vite 内容 hash 产物）固定 `Cache-Control: public, max-age=31536000, immutable`，且 404 不 fallback 到 index.html。改缓存头会影响用户能否看到新前端版本，改动需在 `?view=hof-admin` 等页验证。
- **Build identity**：Build checkout 必须核对完整 source SHA，immutable tag 与 digest 供验证和诊断。TX 的 business-api/frontend 从 Gitee exact SHA 在 TX 本机构建并直接推 TCR，production 只部署 build 输出的 exact digest；Frontend 额外把 `ASSET_BASE_URL` 纳入 image identity，并验证 pinned Agent WASM。尚未迁移到 digest pin 的 owner 不受此条扩展。Yecao parser-worker/ai-service/MinIO 只用 GHCR。business-api 镜像产物名为 `wotbtools-business-api`，内部 Maven module 仍叫 `wotb-web`。
- **Frontend 发布边界（`frontend.yml`）**：GitHub 是 release authority，不再承担 Frontend Docker build/TCR 大镜像上传。workflow 先把 exact GitHub SHA 主动 mirror 到 Gitee，并下载/校验 `deploy/agent/source.json` 锁定的轻量 Agent WASM archive；只把 TX builder 脚本与该小 artifact 暂存到 TX。TX 的 `deploy/tx/build-frontend-from-gitee.sh` 复用 production Gitee clone 与 Business API 共用的 host build lock，创建 exact-SHA worktree、用 SHA256 验证 WASM、构建镜像并在任何 registry 写入前校验 source SHA / `ASSET_BASE_URL` / WASM / 静态文件，随后在国内链路发布 immutable TCR image 并回读 digest。生产必须通过 `TX_FRONTEND_IMAGE_REF=...@sha256:...` 部署该 digest；Frontend 不再发布或依赖 `latest`，也不再使用 GitHub runner 的 `deploy/list-image-tags.sh` / `run-with-network-retry.sh` 发布路径。
- 本地完整 Docker Compose 开发环境已退役；Keycloak realm 集成验证仅使用 `deploy/test-keycloak-tofu.sh` 的 disposable PostgreSQL、Keycloak 与 local OpenTofu state。

- **Komodo 控制平面**：Komodo Core/Mongo 的 bootstrap、升级和 break-glass recovery 由 `.github/workflows/komodo-controller.yml` 独立拥有，runtime 定义在 `deploy/komodo/compose.yml`，DNSPod 声明在 `infra/tofu/komodo`。Komodo 不得管理自己的 Core 生命周期；Core 仅绑定 Yecao WireGuard `10.20.0.2:9120`，公网入口仍由 TX Caddy 独立拥有。首阶段不安装 Periphery，也不迁移任何 workload owner。

## 运维（安全）

- 备份：`.github/workflows/database-backup.yml` 运行 TX owner 的 `business-postgres-backup.sh` 与 `keycloak-postgres-backup.sh`，随后备份 TX/Yecao local Tofu state；normal Deploy 不调用 backup，也不把本地备份描述为 COS。Business restore 只允许校验或恢复到 disposable 数据库，禁止覆盖 authoritative `wotb`；Keycloak 归档不得交给 Business restore 工具。
- 观测：`deploy/observability/`（Alloy config + Grafana dashboards/provisioning）；指标名被 dashboards 引用，改名需同步 JSON。Grafana dashboard API ownership 由 `infra/tofu/grafana` 管理，`.github/workflows/observability.yml` 自己执行 runtime reconcile 与 Grafana Tofu apply；PR 只做本地 validation，不运行 authenticated plan。Prometheus/Loki datasource 仍由 file provisioning 管理。Prometheus 必须验证 backend、ai-service、node-exporter、Prometheus、Loki、Grafana 六类 target 为 `up == 1`；Grafana 必须验证 health、Prometheus/Loki datasource health、全部 dashboard UID API 与 Production Overview 默认首页。Keycloak 不再进入 Prometheus metrics contract，登录/IdP/callback 通过 Alloy → Loki 日志验证。TX 侧 `alloy-tx` 独立固定基础设施车道采集业务日志，经 WireGuard 写入 Yecao Loki；Yecao Prometheus 通过 WireGuard 抓取 TX business-api 的 management 指标，并通过 `wotb_internal` Docker service discovery 抓取本机 `ai-service:8080/actuator/prometheus`。生产上线后的 metrics endpoint、Prometheus target/query、Loki backend/Keycloak/frontend canary stream 由 `deploy/verify-observability.sh` 验证；CI 用 `deploy/test-observability-e2e.sh` 验证真实 Docker emitter → 生产 Alloy → Loki 的三条 ownership path，并用 `deploy/test-grafana-runtime.sh` 验证 datasource provisioning 与 dashboard API adoption。
- 服务 owner workflow 逐个 staging 并执行 readiness；镜像选择遵循各 owner 的当前 release contract：TX business-api/frontend 使用 exact TCR digest，尚未迁移的 owner 才可继续使用其现有 `latest` 约定。生产实际镜像必须通过容器 inspect / artifact metadata 与冻结 source identity 核对。固定上游服务不读取应用发布记录；Yecao 观测失败只输出 `OBSERVABILITY DEGRADED`。
- 生产发布在 staged compose pull 后、live promote 前必须运行 `validate-alloy-config.sh`（Alloy）与 `deploy/tx/validate-caddy-config.sh`（Caddy，由 `deploy/tx/deploy.sh` 的 staged validation 调用）；两者都是 fail-closed：校验失败必须在 live mutation 之前退出，禁止用 `|| true` 或删除校验绕过。Caddy 校验必须显式 `--entrypoint caddy`：官方镜像只声明 `CMD ["caddy","run",…]` 而没有 ENTRYPOINT，直接传 `validate …` 会被 runc 当成可执行文件名（`exec: "validate": executable file not found in $PATH`）。Alloy Android 下载 `stage.match` selector 使用 LogQL 安全的 `[.]`，禁止回退到会触发 `invalid char escape` 的 `\\.` 写法。
- **Immutable reuse 判定按 release lane 归属**：仍在 GitHub runner 发布镜像的 owner 如需枚举 tag，必须走 `deploy/list-image-tags.sh`，只有 registry 明确返回 `NAME_UNKNOWN` 才按首次发布继续；TX 本地构建的 business-api/frontend 则由各自 `build-*-from-gitee.sh` 的 `lookup_remote_digest` 直接解析 immutable tag → digest。两条路径都必须把 401/403/5xx/网络/DNS 视为 fatal，禁止用 `... || true` 把 registry 故障伪装成“镜像不存在”。
- Grafana 生产 API 校验必须复用 `deploy/grafana-api-request.sh` 这条生产 backend Alpine 运行时可用的 BusyBox `wget` 路径：调用方只传 `/api/...`，helper 在 backend 容器内唯一拼接 Grafana hostname 并生成 `Authorization: Basic` header（不得把密码放 URL、命令输出或日志），datasource health 的唯一成功值是 JSON `status=OK`。CI runtime smoke 还必须在 Alpine 3.22 中验证正确凭据通过、错误凭据失败，以防回退到 GNU-only `wget` 参数或 double URL prefix。
- Loki canary 校验在 emitter 启动前固定 `start`，重试时只推进 `end`；响应必须是 `status=success`、至少一个 result stream、至少一个 values 样本并包含 marker。Keycloak canary 是加入 `wotb_internal` 网络的独立 Alpine emitter，只用于验证 Alloy 的 ownership 采集路径，不得把 Keycloak 镜像当 shell 执行。
- Keycloak 运行时契约由 `deploy/test-keycloak-runtime.sh` 独立验证：自定义镜像必须以 `start --optimized` 启动，保留 PostgreSQL 与应用 OIDC discovery；不再启用或暴露 management health/metrics 端口，且不得出现启动时 Quarkus augmentation。启动日志必须报告**运行镜像自身注入的** build commit（`runtime-contract`＝本脚本自建的一次性镜像，或 40 位源码 SHA＝已发布生产镜像），期望值从容器 env 推导。main push 上 `.github/workflows/keycloak.yml` 的 `smoke` 验证 published digest；PR 上 `.github/workflows/ci-keycloak.yml` 的 `keycloak_runtime` 运行真实 Docker smoke。

## Gate boundary

- Blocking production health（Yecao）：`parser-worker` 容器存活（该服务无 HTTP 端点）。业务 API、frontend 与 Keycloak 的 HTTP/OIDC 探测属于 TX deploy（`deploy/tx/deploy.sh`）。
- Non-blocking observability：Prometheus、Loki、Alloy、Grafana、datasources、dashboards、metrics 与 log ingestion。
- `verify-observability.sh` 必须保持 fail-closed；deploy orchestration 负责把失败记录为 degraded，而不是用 `|| true` 改写 verifier 语义。
- 排障：SSH VPS `ssh -i "$env:USERPROFILE\.ssh\wotb_vps_deploy" -o IdentitiesOnly=yes root@45.136.14.101 -p 58361`，`docker logs wotb-parser-worker-1 --tail 100`——Yecao 宿主运行 parser-worker、预部署 ai-service 与观测服务，业务后端日志在 TX；也可运行仅 `workflow_dispatch` 的 `.github/workflows/prod-diagnostics.yml` 只读采集同一批日志。常见根因：凭据缺失导致的 crash loop、broker/MinIO 端点不可达。
- secret 一律 GitHub Secrets / Variables → SSH 运行时 env（仓库根 `.env.example` 只列变量名）；TX 不维护本地 secret env 文件，禁止落库或写死。赞助/收款信息不硬编码进页面或仓库（运行时只读挂载）。
