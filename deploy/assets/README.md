# Alibaba Shanghai asset origin

This directory declares the Komodo-managed static origin for Agent 3D assets.
It does **not** cut production traffic over by itself.

## Runtime ownership

- Komodo Server: `ali-sh-asset-01` (already exists; ResourceSync adopts it by name)
- Stack: `wotbtools-asset-origin`
- Public name: `assets.wotbtools.com`
- Compose source: GitHub is review authority; Gitee is transport for the mainland worker.
- Stack source ref: `branch = "asset-origin"`. This asset-owned Gitee branch is moved
  **only** by `.github/workflows/asset-origin.yml`; the Frontend/Business API mirrors
  can never change what this Stack deploys.
- Source mirror gate: `.github/workflows/asset-origin.yml` checks out the triggering
  GitHub `main` event SHA, publishes that frozen commit to the derived GitHub
  `asset-origin` pointer branch and then to the matching Gitee `asset-origin`
  transport branch, and requires `refs/heads/asset-origin` on Gitee to equal the same
  SHA. It never writes shared Gitee `main`, and it fails closed without pushing when
  the frozen SHA is no longer the exact current GitHub `main`.
- Why the GitHub pointer branch exists: the Frontend/Business API production mirrors
  run a pinned `Yikun/hub-mirror-action` that force-pushes **every** GitHub branch to
  Gitee as `refs/remotes/origin/*:refs/heads/*` with `--tags --prune`. A Gitee-only
  `asset-origin` branch would be deleted by the next application mirror. Publishing
  the same frozen SHA to the GitHub `asset-origin` branch makes it part of the mirrored
  source set, so those mirrors carry the verified SHA instead of pruning it. The
  shared `production-gitee-mirror` concurrency group serializes this job with both
  mirror jobs, so the pair is never updated concurrently.
- Periphery: the Alibaba agent is **manually** bootstrapped and manually
  lifecycle-managed today (see below); it is not part of `komodo-periphery.yml`.
- Payload: host state under `/srv/wotb-assets`, mounted read-only into Caddy.

The asset pack is generated by `WoT-Blitz-Agent`; this repository does not own or
build the game assets.

## Manual Periphery boundary (intentional, deferred)

`ali-sh-asset-01` was onboarded by hand before this Stack was declared, and its
outbound Periphery agent is already connected and healthy. This PR deliberately does
**not** manage that agent's lifecycle:

- no Alibaba target profile, adoption script, SSH secret, or reusable Periphery
  workflow exists in this repository;
- ResourceSync only declares the existing Komodo Server (`address = ""`,
  `enabled = true`, outbound only, no inbound `:8120`), which means "Komodo knows
  this Server", not "GitHub Actions manages its process";
- a host rebuild, a Periphery upgrade, or a manual restart remains a manual
  operation outside this repository for now.

Automating the Alibaba/mainland Periphery lifecycle becomes worthwhile only when one
of these happens: the host is rebuilt, a Periphery upgrade becomes necessary, a
second mainland worker is added, or manual lifecycle management becomes an actual
operational pain point. That future work would add its own reviewed target profile,
lifecycle automation, and (if a second host-local mutation owner exists) a shared
host lock — none of which is part of this PR.

## Host layout

Publish immutable releases and switch the `current` symlink only after the new
release is complete:

```text
/srv/wotb-assets/
  bin/asset_release.py                 # copied from WoT-Blitz-Agent tools/
  bin/asset_store.py                   # content-addressed store tool
  objects/
    <sha[:2]>/<sha256>                 # unique content, one inode per blob
  releases/
    <release-id>/                      # immutable; files are hardlinks to objects
      version.json
      manifest.json
      index.json
      glb/
      map/
      tank/
      tank_images/
      data/
  datasets/
    <dataset-id> -> ../releases/<release-id>
  current -> datasets/<default-id>
  versions.json                        # generated catalog (frontend selector source)
  release-log.jsonl                    # append-only audit
  .publish.lock
```

Keep the current release plus at least one previous release while the migration is
being proven. Do not overwrite the live tree in place. Initial payload upload remains
manual; Git tracks configuration, not the multi-GB asset pack.

## Dataset versions

The origin serves one dataset per game-version channel. Current channels (2026-11-05):

- `supertest` — the supertest/preview channel; re-pointed to each new preview
  release (t11b → t11p2 → …) instead of accumulating per-preview datasets.
- `11.21.0` — the live 11.21 release client.
- `11.22` — reserved; added when the live 11.22 pack ships (three channels
  total: supertest / 11.21 / 11.22).

`datasets/<id>` is a symlink to an immutable release; `current` points at the
default dataset so legacy clients keep working.

**Deployment state (2026-11-05):** the host already contains the object store and
datasets, but the live Caddy Stack still runs the pre-dataset Caddyfile;
`/versions.json` and `/v/<id>/...` return `404` until this file is deployed through the
normal `asset-origin` → Komodo Stack redeploy. `/` and `/version.json` keep serving the
default dataset meanwhile.

Public paths:

| Path | Meaning |
|---|---|
| `/v/<dataset-id>/...` | a specific game-version dataset |
| `/versions.json` | dataset catalog (`schema`, `default`, `datasets[]`) |
| `/v/<dataset-id>/version.json` | immutable release identity |
| `/...` | legacy root = `current` (default dataset) |

Publish a new game version (release directory already staged under `releases/<id>`
with `version.json`/`manifest.json`):

```bash
# on the Alibaba host
bash deploy/assets/dataset.sh link --dataset 11.22.0 --release 20261118-3f9a2c1b
bash deploy/assets/dataset.sh default --dataset 11.22.0        # optional: move legacy root
bash deploy/assets/dataset.sh verify
bash deploy/assets/verify.sh https://assets.wotbtools.com
```

Rebuild the same game version (new release, same dataset id):

```bash
bash deploy/assets/dataset.sh link --dataset 11.21.0 --release 20261105-aaaaaaaa
```

Rollback is the same atomic symlink switch; the catalog records the older release:

```bash
bash deploy/assets/dataset.sh rollback --dataset 11.21.0 --release 20261015-bbbbbbbb
```

Retire a dataset channel (symlink only; the release directory stays for rollback;
fails closed if the dataset is the current default):

```bash
bash deploy/assets/dataset.sh unlink --dataset 11.21.0-t11-preview
```

`dataset.sh` holds `flock` for every mutation, appends `release-log.jsonl`, regenerates
`versions.json` through `asset_release.py`, and runs its `verify` before returning.
`asset_release.py` is the single source of truth; copy it from the Agent repo:

```bash
scp tools/asset_release.py admin@47.101.141.111:/srv/wotb-assets/bin/
```

`versions.json` uses `max-age=60`; versioned content stays at `max-age=300` until the
pack moves to content-addressed paths.

## Content-addressed store (space dedupe)

`objects/<sha[:2]>/<sha256>` holds each unique content blob once; every release tree is
a set of **hardlinks** to those objects. Caddy still serves `/srv/wotb-assets/current`
and `/v/<id>/...` as ordinary static files, so URLs/ETag semantics are unchanged.

Copy the tool from the Agent repo:

```bash
scp tools/asset_store.py admin@47.101.141.111:/srv/wotb-assets/bin/
```

Migration (one-off, content unchanged):

```bash
python3 bin/asset_store.py import --pack releases/<current> --objects objects
python3 bin/asset_store.py adopt --releases releases --objects objects --dry-run
python3 bin/asset_store.py adopt --releases releases --objects objects
python3 bin/asset_store.py stats --objects objects --releases releases
python3 bin/asset_store.py verify --objects objects --releases releases --links
```

New releases:

- Keep the existing `cp -al` + overlay + `--refresh-manifest` flow, then
  `asset_store.py adopt --releases releases/<new> --objects objects` before
  `dataset.sh link`; or
- Object-native: upload the new `manifest.json` + changed files to `incoming-<batch>/`,
  then
  ```bash
  python3 bin/asset_store.py import --manifest incoming/manifest.json \
      --files incoming --objects objects
  python3 bin/asset_store.py materialize --manifest incoming/manifest.json \
      --objects objects --out releases/<new> --metadata incoming
  ```
  then `dataset.sh link --dataset <id> --release <new>`.

After pruning old releases and clearing `incoming-*`, run
`asset_store.py gc --objects objects --releases releases` (`--dry-run` first). GC only
removes objects with no retained-release manifest reference **and** `st_nlink == 1`.
`objects` and `releases` must be on the same filesystem; backups must preserve links
(`rsync -aH`), otherwise the store expands back to logical size. Full contract:
Agent repo `docs/asset-store.md`.

## Caddy image preload contract

The mainland asset host does not reliably reach Docker Hub, so the Stack keeps
`auto_pull = false`. Before the first deploy, after a host rebuild, or whenever the
pinned Caddy tag changes, preload the exact Linux/amd64 image from a trusted host that
can reach the registry.

On the source host:

```bash
docker pull --platform linux/amd64 caddy:2.10.2-alpine
SOURCE_IMAGE_ID="$(docker image inspect caddy:2.10.2-alpine --format '{{.Id}}')"
docker save caddy:2.10.2-alpine -o /tmp/caddy-2.10.2-alpine-amd64.tar
sha256sum /tmp/caddy-2.10.2-alpine-amd64.tar
```

Transfer the archive to `ali-sh-asset-01` out of band. Compare the archive SHA256 on
both ends before loading it. Then on Alibaba:

```bash
sha256sum /tmp/caddy-2.10.2-alpine-amd64.tar
docker load -i /tmp/caddy-2.10.2-alpine-amd64.tar
docker image inspect caddy:2.10.2-alpine \
  --format 'ID={{.Id}} OS={{.Os}} ARCH={{.Architecture}}'
```

The destination image ID must equal `SOURCE_IMAGE_ID`, and the inspection must report
`OS=linux` and `ARCH=amd64`. Only then run the manual Komodo Stack Deploy. Delete the
temporary tar after the destination verification succeeds. Do not use Komodo **Pull
Images** on this host unless Docker Hub reachability has been deliberately restored.

## First rollout

1. Merge the reviewed GitHub change (Server + Stack declarations and the asset
   transport workflow).
2. Require **Asset Origin Source Mirror** to pass. Its exact-SHA push and bounded
   verification prove Gitee `refs/heads/asset-origin` contains the triggering
   reviewed GitHub commit; an account-level mirror, shared Gitee `main`, or
   informal/manual freshness check is not sufficient. A run whose frozen SHA is no
   longer exact current GitHub `main` fails closed without touching its transport
   ref — re-dispatch it on the new exact `main`.
3. In ResourceSync `wotbtools-main`, review the pending diff. The existing
   `ali-sh-asset-01` Server and `wotbtools-asset-origin` Stack must be adopted by
   name; `address` stays empty and no inbound Periphery `:8120` is introduced.
4. Apply the ResourceSync diff by hand. This must not deploy the Stack
   (`deploy = false`).
5. Stage the asset pack under `/srv/wotb-assets/releases/<pack-id>`, verify
   `manifest.json`, then `dataset.sh link --dataset <id> --release <pack-id>` and
   `dataset.sh default --dataset <id>` (see “Dataset versions”). `current` must end up
   at the default dataset, not a raw release directory.
6. Preload and verify `caddy:2.10.2-alpine` using the image preload contract above.
7. Ensure the Alibaba firewall allows public TCP 80/443. Do not expose Periphery
   `:8120`.
8. Point `assets.wotbtools.com` at the server when ready for certificate issuance,
   then explicitly deploy the Stack in Komodo (the only Stack mutation owner).
9. Run `bash deploy/assets/verify.sh https://assets.wotbtools.com`.
10. 修改主 Frontend 与 TX2 replica workflow 中的 tracked `ASSET_BASE_URL` 前，先用
    `?assets=https://assets.wotbtools.com` 对 Web 客户端做 canary。
11. Web 与新 Android 版本统一使用 `https://assets.wotbtools.com`。Android 保留本机
    `/agent-assets` 路由，由 `AgentAssetProxy` 直连该 origin；旧 APK 仍使用编译时 COS
    origin，COS 桶、对象与旧 gateway `/agent-assets` 反代继续保留，供 legacy 客户端和临时回滚使用。

## Caddy config/redeploy contract

`Caddyfile` is a tracked Komodo Stack config dependency with `requires = "redeploy"`
for the `caddy` service. Full/manual Stack deploys also pass `--force-recreate`, so a
Caddyfile-only CORS/cache change cannot report a successful deploy while the old
Caddy process remains in memory. The Caddy admin API stays disabled.

## Cache/CORS contract

Current filenames are not content-addressed. Caddy therefore uses a short
revalidation TTL, not `immutable`. Versioned datasets (`/v/<id>/...`) are immutable
per release, but their filenames are still not content-addressed, so they keep the
same 300s TTL; `versions.json` uses 60s so a publish/rollback is visible quickly.
Browser CORS reflects only `https://wotbtools.com` and `https://www.wotbtools.com`.
`Vary: Origin` is emitted unconditionally on cacheable responses so a shared cache
cannot reuse a no-Origin representation for an allowed browser request. Range and
conditional requests are served by Caddy's static file server; CI exercises the real
Caddy image at request level, and `verify.sh` checks the externally visible behavior
with bounded network timeouts.
