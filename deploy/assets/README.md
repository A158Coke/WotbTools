# Alibaba Shanghai asset origin

This directory declares the Komodo-managed static origin for Agent 3D assets.
It does **not** cut production traffic over by itself.

## Runtime ownership

- Komodo Server: `ali-sh-asset-01`
- Stack: `wotbtools-asset-origin`
- Public name: `assets.wotbtools.com`
- Compose source: GitHub is review authority; Gitee is transport for the mainland worker.
- Source mirror gate: `.github/workflows/asset-origin.yml` force-mirrors `main` and then requires Gitee `main` to equal the exact reviewed GitHub SHA.
- Periphery lifecycle: the Alibaba target under `deploy/periphery/targets/ali-sh-asset-01/` uses the shared repository-owned install/reconcile/verify implementation and is the final dependent job in the single `.github/workflows/komodo-periphery.yml` owner chain (`Yecao -> TX1 -> TX2 -> Alibaba`).
- Payload: host state under `/srv/wotb-assets`, mounted read-only into Caddy.

The asset pack is generated by `WoT-Blitz-Agent`; this repository does not own or build the game assets.

## One-time host adoption prerequisite

The Alibaba host was manually onboarded before it was added to the repository-owned
Periphery lifecycle. The host-side transport prerequisites can be prepared before the
PR merges, but the repository-owned adoption/reconcile itself runs only after the
reviewed workflow exists on `main`.

Before merging:

1. Configure key-only SSH for the `admin` operator and repository secrets
   `ALI_ASSET_VPS_HOST`, `ALI_ASSET_VPS_USER`, `ALI_ASSET_VPS_PORT`, and
   `ALI_ASSET_VPS_SSH_KEY`.
2. Ensure `admin` has the reviewed non-interactive sudo capability needed by the
   shared Periphery reconcile.
3. Create `/opt/wotb-asset` and `/opt/wotb-asset/periphery` as real directories
   owned by `admin`, and create the real `/opt/wotb-asset/.deploy.lock` owned by
   `admin`. The Periphery lifecycle deliberately refuses to create another owner's
   host mutation lock.

After merge, the normal `Komodo Periphery` workflow reaches Alibaba only if Yecao,
TX1, and TX2 all reconcile successfully first. The reviewed `adopt-existing.sh`
bridge takes the host mutation lock and, only if an existing service is already
active, independently proves: persistent identity and Core trust files exist, the
process environment and installed config contain no onboarding credential, the
installed config resolves to the exact reviewed Core/identity/operator semantics,
the process has an established connection to the reviewed Core peer, and no inbound
`:8120` listener exists. Only then does it atomically commit the root-owned mode-0600
`/etc/komodo/keys/onboarding-complete` marker. The same job immediately runs the
normal shared reconcile and must finish credential-free.

The marker contains no credential. The adoption bridge is a no-op on a fresh/rebuilt
host with no active existing Periphery; in that case normal reconcile performs a clean
bootstrap when a fresh Core key has been placed in the optional repository secret
`KOMODO_ALI_ASSET_ONBOARDING_KEY`. The lifecycle never stores that value in Git or the
persistent config.

## Host layout

Publish immutable releases and switch the `current` symlink only after the new release is complete:

```text
/srv/wotb-assets/
  releases/
    <pack-id>/
      index.json
      manifest.json
      glb/
      map/
      tank/
      tank_images/
      data/
  current -> releases/<pack-id>
```

Keep the current release plus at least one previous release while the migration is being proven. Do not overwrite the live tree in place.

## First rollout

1. Complete the host-side SSH/sudo/lock prerequisites above, then merge the reviewed GitHub change.
2. Require **Asset Origin Source Mirror** to pass. Its exact-SHA check proves the Gitee transport contains the reviewed GitHub commit; an informal/manual freshness check is not sufficient.
3. Require the single **Komodo Periphery** workflow to pass through the full dependency chain `Yecao -> TX1 -> TX2 -> Alibaba`. For this already-onboarded host, the Alibaba job must complete adoption and the following normal credential-free reconcile successfully before any ResourceSync Apply.
4. In ResourceSync `wotbtools-main`, review the pending diff. The existing `ali-sh-asset-01` Server and `wotbtools-asset-origin` Stack must be adopted by name; `address` stays empty and no inbound Periphery `:8120` is introduced.
5. Apply the ResourceSync diff. This must not deploy the Stack (`deploy = false`).
6. Stage the asset pack under `/srv/wotb-assets/releases/<pack-id>`, verify `manifest.json`, then atomically point `current` at that release.
7. Ensure Alibaba firewall allows public TCP 80/443. Do not expose Periphery 8120.
8. Point `assets.wotbtools.com` at the server when ready for certificate issuance, then explicitly deploy the Stack in Komodo.
9. Run `bash deploy/assets/verify.sh https://assets.wotbtools.com`.
10. Canary the Web client with `?assets=https://assets.wotbtools.com` before changing the production `ASSET_BASE_URL`.
11. Migrate the Android native asset origin in a separate client change. Old Android binaries keep using the old COS origin until retired.

## Caddy config/redeploy contract

`Caddyfile` is a tracked Komodo Stack config dependency with `requires = "redeploy"` for
the `caddy` service. Full/manual Stack deploys also pass `--force-recreate`, so a
Caddyfile-only CORS/cache change cannot report a successful deploy while the old Caddy
process remains in memory. The Caddy admin API stays disabled.

## Cache/CORS contract

Current filenames are not content-addressed. Caddy therefore uses a short revalidation TTL, not `immutable`. Browser CORS reflects only `https://wotbtools.com` and `https://www.wotbtools.com`. `Vary: Origin` is emitted unconditionally on cacheable responses so a shared cache cannot reuse a no-Origin representation for an allowed browser request. Range and conditional requests are served by Caddy's static file server; CI exercises the real Caddy image at request level, and `verify.sh` checks the externally visible behavior with bounded network timeouts.
