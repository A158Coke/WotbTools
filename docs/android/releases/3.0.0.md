# Android 3.0.0

- versionName: 3.0.0
- versionCode: 3000000
- Native Bridge: v3 (origin / transport change; RPC methods, params, results and capabilities unchanged)
- Version classification: major — the Web runtime is replaced (device System WebView → APK-bundled GeckoView) and the Native Bridge wire contract changes origin, so every 2.x client must update.
- Minimum supported version: raised to 3000000 (3.0.0)

The app no longer renders with the phone's System WebView. It ships its own Mozilla GeckoView stable engine (158.0.20261007201254), so every device runs the engine that was tested for the release instead of whatever WebView version the ROM provides. This targets the Android 9 devices that showed broken CSS and whole-app crashes when the WebView renderer died.

What changes for users:

- The bundled pages are served by the app itself (`LocalRuntimeServer`) from `http://127.0.0.1:21653`, a fixed loopback origin. If that port is already taken (for example by a cloned second copy of the app), the app shows an error page with a retry button instead of loading.
- A Gecko **content-process** crash no longer closes the whole app: the first crash reloads the current page automatically; a second one within a minute shows an error page with "重新加载" / "使用浏览器版" and a selectable diagnostics line. When the system kills the content process to reclaim memory, the page reloads silently when the user returns. A native crash of the Gecko parent process, which runs inside the app process, can still end the app.
- Web downloads and exports work through Gecko's download dispatch: PNG export, Hall of Fame replay download and the tournament XLSX export spool the response body into a private temporary file and then use the system document picker (`ACTION_CREATE_DOCUMENT`); filenames honour `Content-Disposition` (`filename*` first) and MIME hints, and cancelled or failed saves clean up the temporary file.
- HTML `<select>` opens a native menu (single / multiple / menu prompt, optgroups, `disabled` options); the file input keeps using the system picker. Page side dismissal, option updates while open, navigation while a prompt is open, and late picker results all settle exactly one prompt result.
- Saved page preferences from 2.x (language, column layout, playback options, onboarding progress, UI profile) are reset once, because they lived in the old WebView profile. Login sessions and received replays are kept (they are owned by the native app).
- The APK is much larger: the release keeps `arm64-v8a` + `armeabi-v7a` with compressed native libraries (about 160 MiB of engine plus the bundled frontend; debug additionally carries `x86_64`). 2.x was about 15 MB.

Fixed during the pre-merge review of the 3.0.0 release candidate — these are part of 3.0.0, not of any later patch release (no 3.0.x release identity existed before this one):

- **Trusted local blob download navigation.** GeckoView dispatches a download through `NavigationDelegate.onLoadRequest` *before* `ContentDelegate.onExternalResponse` ever sees it, so `<a download>` + `URL.createObjectURL` exports were denied and never reached the download pipeline. Main-frame navigation now also allows `blob:http://127.0.0.1:21653/<uuid>` — scheme `blob`, the embedded origin must be exactly the local origin (no userinfo / query / fragment) and the id must be a canonical UUID. Everything else (other hosts / ports / schemes, malformed blob URLs, `data:`, `file:`, `javascript:`, external `http:`) stays denied, `https:` / `mailto:` still go to the system browser, the subframe policy still accepts only the local origin, and a blob URL is never a trusted application origin: the Native Bridge sender check still accepts only the exact `http://127.0.0.1:21653` origin.
- **Response body ownership in `LocalRuntimeServer`.** The routed `StreamResponse.data` is now owned by a single `sendResponse` that closes it exactly once on every path (HEAD, output-stream open failure, header write failure, body copy failure, flush failure, client disconnect, unexpected exception). The previous structure could leak the file descriptor of a replay, folder, bundled-asset or proxy-cache stream when the socket output stream could not be opened after routing, or when the response head could not be written.
- **Download / picker mutual exclusion.** A web download holds the picker slot from spooling through destination write: file and folder pickers are rejected while one is in flight, a download requested while a picker is open is rejected before spooling and its response body is closed, and a later picker can no longer cancel an accepted download. Cancellation, failure and success all clear the state, and a late picker result never reaches a newer prompt.

This candidate also carries everything merged into `main` for the unstaged, unpublished 2.5.0 and 2.6.0 candidates: bounded product usage telemetry (`2.5.0.md`) — it posts to `/api/observability/events`, which Android resolves to `https://wotbtools.com` and which the `@androidLoopback` CORS block already covers (`/api/*`) — and the 2D basemaps bundled at the same bytes as Web with the COS OTA channel (`2.6.0.md`) — on Android the OTA index and images are read from the same-origin `/agent-assets/map2d/…` path, which `LocalRuntimeServer` routes to `AgentAssetProxy`, so no extra CORS or CSP is needed. Bundling the full-size basemaps adds roughly 11 MiB to the APK.

Unchanged: the bundled Vue frontend and local WASM parsing, native QQ / Keycloak login through the system browser, replay sharing / opening / folder import, APK self-update, connectivity handling, the declared permission set (GeckoView merges the install-time `WAKE_LOCK` and `MODIFY_AUDIO_SETTINGS` permissions; page permission requests are always denied).

Release prerequisites, in order (the canonical runbook is "3.0.0（GeckoView）发布与回滚" in `docs/android/release-process.md`): ① **set the repository variable `ANDROID_MIN_SUPPORTED_VERSION_CODE=3000000` before this candidate is merged** — the stage preflight runs the same cutover guards (`guard_min_supported` / `guard_local_first_cutover` / `guard_bridge_covered`), so the floor is a *stage* prerequisite, not just a publish one; setting it does not touch production `version.json` and does not force 2.x clients to update, and after it is set no 2.x candidate may be staged or published; ② merge this PR to `main`; ③ the merge automatically runs both the Caddy Gateway deployment (`caddy.yml`, which ships `@androidLoopback` for the exact `http://127.0.0.1:21653` origin) and the automatic stage of 3.0.0 — the gateway change lives in this PR and the production Caddy workflow only runs from fresh `main`, so it is deployed after the merge, never before it and never by hand; ④ wait until **both** the Caddy production deployment and the 3.0.0 stage have succeeded; ⑤ real-device acceptance on an Android 9 device and an Android 13+ device — including the blob export / download items, which CI cannot cover — plus the network observation; ⑥ `publish(version=3.0.0)`, the only commit point for the Android client rollout (it writes production `version.json`, which is what makes 2.x clients update; the Caddy gateway change has already reached production after the merge, and publish's readiness step fails closed if the loopback CORS is not live).

Version identity: 3.0.0 is consumed as soon as **any one** immutable artifact exists — the `android-v3.0.0` tag, the staged APK materialized and SHA-256 verified on **either** TX1 or TX2, the staging evidence, or a published `version.json`. A stage that fails after TX1 was seeded has already locked 3.0.0: the same commit can be re-staged only while it is still `origin/main` HEAD (the APK embeds `buildCommit`). Once 3.0.0 is locked, any change that alters the Android candidate (native code, build inputs, the bundled frontend / WASM / assets, the Native Bridge contract) needs a higher version, while unrelated docs / Caddy / infrastructure changes do not, and a fully staged 3.0.0 is still published from its tag through the usual publish guards. The replaceable Tsinghua replica alone does not consume the version. Rollback is a later 3.0.x release (see "3.0.0（GeckoView）发布与回滚" in the release process); 2.x is no longer a valid production target after this release.

This document records the candidate scope; staging, real-device acceptance and production publication remain separate release steps.
