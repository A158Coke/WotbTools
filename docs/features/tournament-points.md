# 积分赛榜单与截图统计

主维护语言：中文；英文翻译待补。HTTP 形状以 `contracts/http/openapi.yaml` 为唯一来源。

## 页面与权限

- `?view=tournament-points`：公开积分榜。无需登录，按年份、区服和季赛选择赛事，只展示已最终确认的成绩。
- `?view=tournament-points-config`：管理员配置赛事和每轮积分规则。
- `?view=tournament-points-admin`：管理员上传、核对、暂存、发布和修正成绩。

公开入口在「更多 → 工具 → 积分赛榜单」。管理页面及业务/图片识别接口要求 `tournament-admin` 或 `wotbtools-admin`；联赛管理员不具有用户管理、名人堂审核或其它管理权限。所有有联赛权限的管理员共享同一份当天草稿；公开接口不返回草稿、未发布军团、小组截图或识别材料。

角色由 `infra/tofu/keycloak/roles.tf` 管理，随 Keycloak owner 发布创建，不是默认角色。为具体用户分配角色需在 Keycloak 的用户角色映射中操作；重新登录后新 token 才携带新权限。前端侧栏、手机「更多」、业务 `/api/admin/tournaments/**` 和独立 AI 截图识别入口使用相同的角色边界。

## 赛事和积分规则

赛事身份为「年份 + 区服 + 季赛」，组合不能重复。区服为国服、亚服、美服、欧服；季赛包含春、夏、秋、冬和战火杯。管理员选择 4–5 轮，每轮 2–3 天，不按区服固定。

每轮单独填写所有天的积分规则，第 1–4 名必填，第 5 名可选。整轮所有天规则完整后才开放该轮统计；只填某一天不能开放。其它轮尚未配置，不影响已完成配置的轮。

规则分值为 0–1,000,000 的整数。遇到五队小组而当日未配置第五名时，需要先补规则，不能将未配置分值默认为 0。显示名可采用 Day 1/2/3 或小组赛/决赛圈，第三天及其它天的展示标签可以编辑；标签不改变日的身份。

开始统计后锁定赛事轮数和天数。只有草稿的轮仍可修改积分规则并重新计算；该轮任意一天已最终确认后，整轮积分规则锁定。展示标签仍可改。

## 上传与核对

1. 在统计页面选择赛事、轮和天，先填写当天「应上传小组数」。此字段不放在规则配置页。
2. 上传 PNG/JPEG 截图，每张一个完整小组，3–5 支队伍。每张最多 10 MiB，边长 16–8192 像素，最多 2000 万像素。一图多组需要先裁剪，同组不能跨图拼接。
3. 点击识别。系统逐图显示结果和失败，失败图片可单独重试，不会自动发布。
4. 对照原图核对小组号、军团简称和名次；识别不清楚的字段须修正。截图没有组号时须补组号，没有明确名次时按从上到下排序，`3–4` 按第四名计分。
5. 只持久化军团简称，保留 `-KSR-` 等简称自身符号，不保存其后的队伍长名称。新军团须确认新增，已有简称复用；疑似不同拼写不能由 AI 自动合并。
6. 已上传的小组提示替换或跳过；同一天同一军团出现在不同组时，处理冲突后才可保存有效结果。

AI 负责识别原始排名；唯一算分实现位于业务后端，按规则重新汇总有效日记录。替换小组不会再次累加旧分。AI 不能可靠发现所有被裁掉的行，管理员须核对原图完整性。

## 草稿和最终确认

「暂存草稿」保存管理员共享的当前记录，允许小组未齐和后续增量补传，公开榜单保持原正式成绩。草稿中的军团和分数不会成为公开成绩。

「最终确认」再次弹窗确认，并要求当日有效小组数量等于应上传数、整轮规则就绪、所有军团和排名有效且无重复冲突。发布在一个数据库事务内完成，随后普通上传被锁定。重复提交同一次确认不会再加一遍积分。

共享编辑通过赛事、规则和日版本检查。别人修改后，旧页面收到版本冲突，必须刷新最新草稿，不能覆盖新版本。在图片识别期间切换赛事、轮、天或账号，会作废旧请求结果。

表格顺序为排名、军团简称、总分、各轮每一天的分数及该轮总分。总分降序，同分并列，例如 1、1、3；同分行按简称稳定排列。尚无成绩显示「—」，已确认清分显示 0。

## 历史积分表导入

管理员在统计页选择已经建立的赛事，在「导入历史榜单」选择 JSON 文件，核对服务端预览并再次确认「正式导入并公开」。仅没有草稿、正式成绩或清分记录的赛事允许一次导入，不覆盖已有数据。不需要伪造小组号、截图或名次。

文件最大 2 MiB，包含 `year`、`region`、`season`、`roundCount`、`daysPerRound`、`sourceName`、`sourceSha256` 和 `rows`。赛事身份与维度须与当前选择严格一致。`sourceSha256` 为原始资料的 64 位小写 SHA-256；每行只有 `clanTag`、`points` 和 `sourceTotal`。`points` 按第一轮第一天、第一轮第二天……依次排列，长度必须等于轮数乘天数，格子为 0–1,000,000 的整数或 `null`。未参赛用 `null`，不是 0；`sourceTotal` 必须等于该原始行的非空分数之和。

同军团多行的跨日记录合并；同一天两个非空分数视为冲突，须先核对。后端统一重算轮总分、总分和并列排名；全空/零分报名军团也可保留，但未发布的普通草稿军团仍不公开。历史预览不写库；正式导入在一个事务内完成，记录操作者、来源名称/哈希、输入矩阵和前后状态，相同幂等键与相同内容重试不会再次写入。

接口为 `POST /api/admin/tournaments/{eventId}/historical-import/preview` 和 `POST /api/admin/tournaments/{eventId}/historical-import`。请求格式以 OpenAPI 为准；正式请求还需 `confirm=true` 和稳定的 `idempotencyKey`，网络结果不确定时必须保留该键重试。公开查询使用同一数据库快照，发布并发时不会把新名单与旧积分混在一起。

历史逐日分数与普通名次小组来源在数据库中互斥。已导入的日被锁定；未知积分规则可以一次补完整后锁定，补规则不会重算历史分数。补齐整轮规则后，管理员可使用原有整天全量修正，把该日替换为真实小组统计；修正期间旧正式成绩保持可见，清分记录继续生效。没有任何分数的整天保持未发布，后续正常统计仍要求整轮规则就绪。删除赛事会同时删除历史数据和本届审计。

## 公开榜单导出

公开页选择赛事并加载正式榜单后，可用「导出」菜单导出当前季赛，不包含管理员草稿。加载、错误、空榜单或正在导出时不可再次导出；点击时冻结当前赛事、积分和语言，过程中切换赛事不会串入其它季赛。

- **Excel**：`.xlsx` 文件，标题/文件名含年份、区服和季赛，表头沿用当前语言及日展示方式，包含每轮每天与每轮总分。分数使用数值单元格，未参赛格为空，军团简称为文本；冻结排名/军团列及标题行，支持筛选。
- **PDF**：打开独立打印窗口，选择「另存为 PDF」。两天制采用 A4 横向、三天制采用 A3 横向，每页重复赛事标题与表头，完整列与中文保留，行不跨页；不打印导航、后台控件或界面背景。需允许浏览器打开打印窗口。Android WebView 显示系统浏览器提示，未新增 Native 打印桥接。

屏幕表格、Excel 和打印文档使用同一份积分榜列投影，使用公开 API 的正式值，不在导出层再算积分。`exceljs` 仅在导出时加载，PDF 使用浏览器原生打印，不增加 PDF 库或字体包。

## 发布后的修正

- **整天全量重传**：选择已发布的轮和天，填写原因与应上传组数，重新上传全部小组。旧正式数据在修正草稿期间仍可查看；再次最终确认时原子替换当天，其他天不变。
- **军团清分**：按某天或整轮将指定军团积分清零，填写原因。清分覆盖在后续全量替换时保留；恢复必须通过明确的管理员恢复操作，不能靠重传隐式恢复。
- 修正保存操作者、时间、原因及前后记录，轮总分、赛事总分和名次统一重算。

可丢弃当天草稿/修正草稿而不删除旧正式成绩；删除整届赛事须二次确认，只删除本届赛事的数据和不再被引用的附件。

## AI 接入与运行时配置

图片识别继续使用独立 `java/wotb-ai` 服务的现有 `AI_API_KEY` 和 `AI_BASE_URL`。`TOURNAMENT_RECOGNITION_MODEL` 默认 `deepseek-flash`，仅作用于积分截图，不改变复盘的 `AI_MODEL`。

`TOURNAMENT_RECOGNITION_SIGNING_KEY` 是至少 32 字节的内部随机签名值，作为 GitHub Secret 同时注入 Business API 和 AI Service。它不属于 AI 供应商，不需要另申请 API key。业务后端确认规则和日状态后，对图片 SHA-256、管理员、赛事、轮/天和规则版本签发至多五分钟的识别许可；前端携带原图片和许可直连独立 AI Service。跨服务器时间校验允许最多 30 秒的时钟偏差，许可自身的签发到过期时间仍不得超过五分钟。AI 再次校验真实管理员 JWT 和许可，业务后端在保存/发布时重新检查当前版本。

缺少签名配置时识别不可用，既有公开成绩和 AI 复盘不受影响。截图识别默认最多两个并发、每分钟最多 60 次准入，单次模型调用预算 90 秒。实际 provider 仍可能超时或识别不准；失败不会自动保存/发布，管理员可以重试。

## 存储与验证

赛事状态、军团、草稿/正式 snapshot 和审计保存在 Business PostgreSQL；截图在既有数据卷的赛事独立命名空间。未关联的上传附件 24 小时后清理，已关联草稿、正式记录或审计的证据随赛事保留。删除按本域 FK 和引用顺序执行，不删除 HoF、三环或其他赛事仍引用的附件。

关键验证包括按整轮配置闸门、精确积分及并列排名、重复上传/跨组冲突、版本冲突、正式/草稿隔离、最终确认幂等、清分和整天修正、真实 PostgreSQL migration/事务、图片 permit/gateway/JSON 解析，以及前端三语、路由和管理门禁。普通测试不调用付费 AI；真实识别准确率须另行明确执行 `ai-live` probe。
