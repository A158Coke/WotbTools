# 联赛积分榜与截图统计

主维护语言：中文；英文翻译待补。HTTP 形状以 `contracts/http/openapi.yaml` 为唯一来源。

## 页面与权限

- `?view=tournament-points`：公开积分榜。无需登录，首次进入默认加载国服最新且已有正式成绩的赛事；先按年份、再按春 → 夏 → 秋 → 战火杯 → 冬判断先后。任一轮中只要有一天已最终确认就符合默认展示条件，草稿不算；跳过尚无正式成绩的赛事。没有国服赛事时选择其它区服中最新且有正式成绩的赛事。所有候选都无正式成绩时提示尚无成绩，不默认展示空榜；刷新会重新查找。用户仍可通过年份、区服和季赛查看历史赛事，只展示已最终确认的成绩，刷新保留当前选择。
- `?view=tournament-points-config`：管理员配置赛事和每轮积分规则。
- `?view=tournament-points-admin`：管理员上传、核对、暂存、发布和修正成绩。

管理页沿用公开榜单的纯色卡片、金色赛事强调与轮次分组表头。配置页在赛事选择区提供
「新建赛事」，表单末尾的「创建赛事 / 保存赛事配置」提交当前内容；全局默认、赛事结构、
日展示名称与每轮积分分区呈现，原有默认规则确认和锁定条件不变。
统计页未选择赛事时显示选择指引，成功加载且确实没有赛事时才引导创建；选中后显示赛事、
轮数和每轮天数摘要。CSV、历史 JSON 保持独立入口；比赛日选择与状态就近展示。
管理员预览和导入预览复用公开表格的分组、隔行底色和总分强调，但不展示公开榜单的发布

手机表单单列、名次积分双列，宽表只在表格内部滚动。

## 赛事和积分规则

赛事身份为「年份 + 区服 + 季赛」，组合不能重复。区服为国服、亚服、美服、欧服；季赛包含春、夏、秋、冬和战火杯。管理员选择 4–5 轮，每轮 2–3 天，不按区服固定。

每轮单独填写所有天的积分规则，第 1–4 名必填，第 5 名可选。整轮所有天规则完整后才开放该轮统计；只填某一天不能开放。其它轮尚未配置，不影响已完成配置的轮。

规则分值为 0–1,000,000 的整数。遇到五队小组而当日未配置第五名时，需要先补规则，不能将未配置分值默认为 0。显示名可采用 Day 1/2/3 或小组赛/决赛圈，第三天及其它天的展示标签可以编辑；标签不改变日的身份。

开始统计后锁定赛事轮数和天数。只有草稿的轮仍可修改积分规则并重新计算；该轮任意一天已最终确认后，整轮积分规则锁定。展示标签仍可改。

### 全局默认积分规则

配置页在赛事选择器下方显示默认配置卡片。“设为全局默认配置”滑动开关针对当前赛事的整套已保存规则，不是当前选中的一轮。全部轮次完整且没有未保存修改后才可设置。已有默认时显示“当前已有默认的积分规则配置，是否更新默认配置？”，选择“取消”不改变配置，选择“是，继续更新”原子替换默认。

顶部季赛下拉中的“全局默认配置”直接打开全局规则编辑，无需选择年份和区服。下方季赛固定显示“全局默认配置”并禁用下拉，年份、区服不参与全局配置；各轮编辑内容保留，保存时提交完整规则。页面不展示“当前默认来源”，也不会为全局规则创建假赛事。

默认配置跨年份、区服和季赛全局唯一，也允许关闭。当前来源赛事修改规则后，需要显式更新默认；普通保存不会悄悄改变其它季赛。关闭默认需要确认，已固定规则和季赛单独配置不受影响。初始化默认或来源赛事已删除时，卡片仍可显示和清除默认，不要求虚构一个来源赛事。

规则来源有三种：

- **继承全局默认**：尚未单独配置、尚未开始统计，读取当前默认。5 轮默认可服务前 4 轮，按轮号和天号匹配；缺少所需轮/天时仍要求补齐，不推测积分、不自动改赛事结构。
- **本季赛单独配置**：整套季赛优先，包括已有部分轮次配置的旧赛事，不混入另一套默认。继承时首次保存单独规则，会先保留当前有效整套规则，再覆盖所编辑轮次。
- **已固定规则**：开始统计时固定当时规则，之后更换或关闭全局默认不会改变该季赛草稿或已发布积分。首次保存应上传小组数即进入此阶段，规则固定和统计动作在同一事务中完成。已有赛事和历史导入成绩保持原值，历史未知规则仍走明确的补规则流程。

规则值不携带来源赛事的年份、区服、季赛、日展示名称或应上传小组数。已发布轮仍不可普通编辑，只有草稿的轮仍支持原有修改规则与重算流程。默认状态及赛事状态使用版本检查；其它管理员更换默认后，旧页面须刷新重试，不会以新默认悄悄提交旧预览。

管理员接口为 `GET/PUT/DELETE /api/admin/tournaments/rules/default`、直接编辑全套默认的 `PUT /api/admin/tournaments/rules/default/configuration` 和 `GET /api/admin/tournaments/{eventId}/rule-source`，沿用 `tournament-admin` 权限。新增状态独立返回，原有赛事和日期响应格式保持兼容。现有赛事列表增加 `X-Tournament-Default-Rules: 1` 响应头；新前端通过 HEAD 该已知路径检测能力，旧后端没有响应头时隐藏新增功能，权限和服务错误正常显示，不把未知接口的服务器错误伪装为正常降级。

Android 的两个受信任 origin 由现有 Caddy CORS 配置允许 HEAD 并暴露上述响应头；须部署业务后端及网关后再验证新客户端。此改动不放宽 origin 或身份权限，包内前端随 3.1.0 候选版本提供，不改变 Native Bridge 或既有强制更新门槛。

## 上传与核对

1. 在统计页面选择赛事、轮和天，先填写当天「应上传小组数」。此字段不放在规则配置页。
2. 上传 PNG/JPEG 截图，每张一个完整小组，3–5 支队伍。每张最多 10 MiB，边长 16–8192 像素，最多 2000 万像素。一图多组需要先裁剪，同组不能跨图拼接。
3. 点击识别。系统逐图显示结果和失败，失败图片可单独重试，不会自动发布。
4. 对照原图核对小组号、军团简称和名次；识别不清楚的字段须修正。截图没有组号时须补组号，没有明确名次时按从上到下排序，`3–4` 按第四名计分。
5. 只持久化军团简称，保留 `-KSR-` 等简称自身符号，不保存其后的队伍长名称。新军团须确认新增，已有简称复用；疑似不同拼写不能由 AI 自动合并。
6. 已上传的小组提示替换或跳过；同一天同一军团出现在不同组时，处理冲突后才可保存有效结果。

AI 负责识别原始排名；唯一算分实现位于业务后端，按规则重新汇总有效日记录。替换小组不会再次累加旧分。AI 不能可靠发现所有被裁掉的行，管理员须核对原图完整性。

## 草稿和最终确认

「暂存草稿」保存管理员共享的当前记录，允许小组未齐和后续增量补传，公开榜单保持原正式成绩。草稿中的军团和分数不会成为公开成绩。

「最终确认」再次弹窗确认，并要求当日有效小组数量等于应上传数、整轮规则就绪、所有军团和排名有效且无重复冲突。发布在一个数据库事务内完成，随后普通上传被锁定。重复提交同一次确认不会再加一遍积分。

共享编辑通过赛事、规则和日版本检查。别人修改后，旧页面收到版本冲突，必须刷新最新草稿，不能覆盖新版本。在图片识别期间切换赛事、轮、天或账号，会作废旧请求结果。

表格顺序为排名、军团简称、总分、各轮每一天的分数及该轮总分。总分降序，同分并列，例如 1、1、3；同分行按简称稳定排列。尚无成绩显示「—」，已确认清分显示 0。

公开榜单以赛事标题框展示年份、区服与季赛，右侧仅有参赛军团数及已发布比赛日。军团数为当前公开榜单的 `rows.length`，已发布比赛日为已返回 `days` 中 `published` 为 true 的数量；两项在前端随榜单派生，不新增接口请求、数据库读取或整表排名计算。未添加最高积分、并列名次提示或前三名模块。

公开榜单、管理员预览及导入预览共用按轮分组的两级表头及强调色下划线，总分与轮总分保持各自原列位置，保留所有日分、轮总分、官方排名和行顺序。宽表在自身区域滚动，表头与军团列固定；Showcase 与 Classic 共用结构并使用语义配色。赛事标题框及参赛军团数、已发布比赛日摘要仍仅在公开页展示；管理员预览仍包含共享草稿，Excel/PDF 的数据投影、导出入口与导出契约保持原样。

## CSV 积分导入与持续更新

统计管理页提供独立的「CSV 积分导入」区块，与下方一次性的历史 JSON 导入分开。管理员先选择年份、区服和季赛，再选择 CSV、点击预览并核对目标赛事及变化，最后确认「替换当前季赛积分」。只有 `tournament-admin` 可执行，普通公开榜单不能上传或修改。

CSV 必须是本季赛**更新到当日的完整累计表**。每次提交整体替换当前成绩，不在已有积分上累加；第二天的文件应同时保留第一天和第二天分数。文件里的空白替换为未参赛，原来有分数的格子会被清空；文件不再包含的军团从当前公开名单移除。预览展示导入后榜单，以及新增、变化、移除的军团和积分格数量，管理员确认后才写入。

### 文件格式与校验

- 最大 2 MiB、最多 10000 条数据，UTF-8 编码，支持 BOM、CRLF/LF、标准 CSV 引号和逗号转义。
- 必需表头为 `军团标签`、赛事配置对应的所有 `R1D1…R<n>D<n>` 列，以及 `总积分`；`积分排名` 可作为参考列。列按名称匹配，缺失、重复或额外未知列均报错。
- 空积分格为 `null`；填写 `0` 是明确的零分。积分须为 0–1,000,000 的整数，每行总积分须等于该行逐日分数之和。
- 后端核对总分并统一计算轮总分、赛事总分和并列排名，不信任文件排名，也不依据默认名次规则重新给 CSV 分数打分。同军团的非重叠日期可合并；同日冲突必须先修正文件。
- 文件不包含年份/区服/季赛时，以管理员当前明确选择的目标为准，不从文件名推断，也不自动创建赛事。
- 格式错误通过稳定错误码和行号、列、原因定位；无效编码、坏引号、非法军团、负分、小数、超限和总分不符都不会部分导入。

### 替换、并发与审计

预览不写数据库，旧公开榜单保持可见。正式提交重新校验 CSV 的原始 SHA-256 与预览一致，并在同一赛事锁和数据库事务中替换所有日成绩、公开名单和版本；公开查询只能看到完整旧版或完整新版。发生任何异常时回滚，不保留半套新积分。

存在尚未提交的共享草稿或进行中的修正时拒绝 CSV 替换，管理员须先完成或丢弃工作区。既有清分覆盖保留，预览与最终榜单均按实际生效的清分结果展示；新 CSV 不会暗中恢复已清分成绩。CSV 成绩只对当天实际存在的分数应用清分，空白继续表示未参赛；保留的清分覆盖仍约束后续导入的成绩。移除军团不会因为旧名单标志重新出现在榜单中，历史审计和证据仍保留。

同一幂等键和同一内容的网络重试不重复写入；相同键不同内容拒绝。较早的请求在后续导入后迟到，不得覆盖更新的成绩；文件或赛事版本发生变化时必须重新预览。每次成功替换记录操作者、时间、原文件名和 SHA-256、规范化行、变化与前后状态。被替换的截图小组按轮次、日期保存在审计前状态中，原截图引用继续受证据保留机制保护。原 CSV 文件本身不另行长期存储，记录随本届赛事的现有审计保留和删除。

管理页的修改记录列表仅查询操作摘要，不加载或传输整批 CSV 快照；完整前后记录仍保存在数据库中供内部审计、幂等和证据引用使用。`GET /api/admin/tournaments/{eventId}/audit` 的既有响应字段保持不变，其中 `before`、`after` 以空对象表示列表未包含快照。仅配置了应上传组数、尚无正式成绩的未来日期在 CSV 对应列为空时保留配置，不要求每日重复填写。

证据定时清理与丢弃草稿只查询数据库投影出的去重截图 ID，不将完整审计快照加载到 Java。CSV 审计仅从替换前的 `publishedDays` 提取引用，跳过源积分行与前后榜单；其它历史操作继续识别前后状态中的截图引用。

接口为 `POST /api/admin/tournaments/{eventId}/csv-import/preview` 与 `POST /api/admin/tournaments/{eventId}/csv-import`，均使用 multipart 的 `file` 和 `expectedEventVersion`；正式导入另需预览返回的 `sourceSha256`、`confirm=true` 和稳定的 `idempotencyKey`。完整字段以 OpenAPI 为准。

### 永久数据来源标识

本季赛首次成功 CSV 导入时，在同一事务内将 `csv_imported` 置为 true。公开积分榜在赛事选择器和表格之间显示「数据来源」及 [`_EK_`](https://b23.tv/rqx5iYX) 跳转按钮。后续 CSV 替换、截图修正、清分或清空成绩都不移除此标识；只删除整届赛事时一起移除。预览、失败和其它未用 CSV 的季赛不显示该标识。

公开来源查询为 `GET /api/tournaments/{eventId}/data-source`，只返回来源状态和固定归属信息，不返回上传文件、未发布记录或管理员信息。原赛事/日期/榜单 JSON 形状保持兼容；现有公开和管理赛事列表以 `X-Tournament-Csv-Import: 1` 响应头声明能力，旧后端无标记时新前端隐藏新增入口。既有 Android origins 由 Caddy 暴露此响应头，不放宽跨域来源或管理权限。

来源查询和 CSV 能力探测独立于榜单、管理编辑数据加载。辅助请求失败时单独提示并可用刷新重试，已经获取的榜单、导出和赛事编辑继续可用；不会把上一个季赛的来源展示到当前季赛。

`V34__add_tournament_csv_source.sql` 仅新增永久来源布尔列，既有赛事默认 false，不改变历史积分。CSV 本身不会随着程序部署自动导入，管理员仍须预览确认。首次与后续真实文件验证使用 2026 战火杯原始 CSV：200 支军团、200 个首日分数、1800 个未参赛空格、合计 206408；后续日期测试由原件派生，验证不会重复加首日分数。

## 历史积分表导入

管理员在统计页选择已经建立的赛事，在「导入历史榜单」选择 JSON 文件，核对服务端预览并再次确认「正式导入并公开」。仅没有草稿、正式成绩或清分记录的赛事允许一次导入，不覆盖已有数据。不需要伪造小组号、截图或名次。

文件最大 2 MiB，包含 `year`、`region`、`season`、`roundCount`、`daysPerRound`、`sourceName`、`sourceSha256` 和 `rows`。赛事身份与维度须与当前选择严格一致。`sourceSha256` 为原始资料的 64 位小写 SHA-256；每行只有 `clanTag`、`points` 和 `sourceTotal`。`points` 按第一轮第一天、第一轮第二天……依次排列，长度必须等于轮数乘天数，格子为 0–1,000,000 的整数或 `null`。未参赛用 `null`，不是 0；`sourceTotal` 必须等于该原始行的非空分数之和。

同军团多行的跨日记录合并；同一天两个非空分数视为冲突，须先核对。后端统一重算轮总分、总分和并列排名；全空/零分报名军团也可保留，但未发布的普通草稿军团仍不公开。历史预览不写库；正式导入在一个事务内完成，记录操作者、来源名称/哈希、输入矩阵和前后状态，相同幂等键与相同内容重试不会再次写入。

接口为 `POST /api/admin/tournaments/{eventId}/historical-import/preview` 和 `POST /api/admin/tournaments/{eventId}/historical-import`。请求格式以 OpenAPI 为准；正式请求还需 `confirm=true` 和稳定的 `idempotencyKey`，网络结果不确定时必须保留该键重试。公开查询使用同一数据库快照，发布并发时不会把新名单与旧积分混在一起。

历史能力与提交状态通过独立 `GET /api/admin/tournaments/{eventId}/historical-import?roundNumber=1&dayNumber=1` 查询；原有日期响应格式保持不变，不附加历史字段。后端按提交标记和实际空赛事条件返回一次性导入是否可用，即使名单全部为 `null`、所有日期仍未发布，提交后也不会再次开放导入。

前后端可以独立发布：旧前端仍能严格校验新版后端的原有日期响应；新前端连接不支持历史查询的旧后端时，将其 404 视为历史能力尚不可用，关闭该入口并保留普通积分管理。权限拒绝和服务器错误仍正常显示，不作为旧版本忽略。

历史逐日分数与普通名次小组来源在数据库中互斥。已导入的日被锁定；未知积分规则可以一次补完整后锁定，补规则不会重算历史分数。补齐整轮规则后，管理员可使用原有整天全量修正，把该日替换为真实小组统计；修正期间旧正式成绩保持可见，清分记录继续生效。没有任何分数的整天保持未发布，后续正常统计仍要求整轮规则就绪。删除赛事会同时删除历史数据和本届审计。

### 2026 国服夏季赛一次性数据导入

`V30__import_2026_cn_summer_top32.sql` 固定保存已核对的最终榜前 32 支军团，含 316 个有效每日成绩、4 个未参赛空格。后端正常部署启动时由既有 Flyway 自动执行一次，无需额外工作流或管理员上传；名次、各轮总分和总分仍由现有公开榜单计算。其它军团及赛事不在这次导入范围内，历史导入页面继续保留。

脚本创建或复用 `2026 / CN / SUMMER` 的 5 轮、每轮 2 天赛事。新赛事使用「小组赛 / 决赛圈」，现有空赛事的日名称与积分规则保留；未配置的规则保持未配置，不根据总榜推断小组名次。正式成绩保存于历史分数来源，配置结构及已发布日按原有规则锁定。

全部写入与 `flyway:V30` 审计在同一事务中完成。已有成绩、草稿、清分或不同轮天配置时拒绝覆盖并回滚，部署会明确失败，需先核对冲突；相同批次重跑只跳过，不覆盖后续修正或清分。来源图片 SHA256、原始逐日分数、原图总分和导入指纹保存在导入审计中。

SQL 也可在已执行 V29 的目标业务库中单独执行；正常流程优先使用 Flyway。脚本不读取密钥、不修改账号权限；如果导入后需要修正，使用积分管理中的清分/恢复或整天修正，不修改已经执行的迁移文件。

## 公开榜单导出

公开页选择赛事并加载正式榜单后，可用「导出」菜单导出当前季赛，不包含管理员草稿。加载、错误、空榜单或正在导出时不可再次导出；点击时冻结当前赛事、积分和语言，过程中切换赛事不会串入其它季赛。

- **Excel**：`.xlsx` 文件，标题/文件名含年份、区服和季赛，表头沿用当前语言及日展示方式，包含每轮每天与每轮总分。分数使用数值单元格，未参赛格为空，军团简称为文本；冻结排名/军团列及标题行，支持筛选。
- **PDF**：打开独立打印窗口，选择「另存为 PDF」。两天制采用 A4 横向、三天制采用 A3 横向，每页重复赛事标题与表头，完整列与中文保留，行不跨页；不打印导航、后台控件或界面背景。需允许浏览器打开打印窗口。Android GeckoView 显示系统浏览器提示，未新增 Native 打印桥接。

屏幕表格、Excel 和打印文档使用同一份积分榜列投影，使用公开 API 的正式值，不在导出层再算积分。共享 XLSX capability 是唯一 ExcelJS renderer，`exceljs` 仅在导出时加载；PDF 使用浏览器原生打印，不增加 PDF 库或字体包。

## 发布后的修正

- **整天全量重传**：选择已发布的轮和天，填写原因与应上传组数，重新上传全部小组。旧正式数据在修正草稿期间仍可查看；再次最终确认时原子替换当天，其他天不变。
- **军团清分**：按某天或整轮将指定军团积分清零，填写原因。清分覆盖在后续全量替换时保留；恢复必须通过明确的管理员恢复操作，不能靠重传隐式恢复。
- 修正保存操作者、时间、原因及前后记录，轮总分、赛事总分和名次统一重算。

可丢弃当天草稿/修正草稿而不删除旧正式成绩；删除整届赛事须二次确认，只删除本届赛事的数据和不再被引用的附件。

## AI 接入与运行时配置

图片识别继续使用独立 `java/wotb-ai` 服务的现有 `AI_API_KEY` 和 `AI_BASE_URL`。`TOURNAMENT_RECOGNITION_MODEL` 默认 `deepseek-flash`，仅作用于积分截图，不改变复盘的 `AI_MODEL`。

`TOURNAMENT_RECOGNITION_SIGNING_KEY` 是至少 32 字节的内部随机签名值，作为 GitHub Secret 同时注入 Business API 和 AI Service。它不属于 AI 供应商，不需要另申请 API key。业务后端确认规则和日状态后，对图片 SHA-256、管理员、赛事、轮/天和规则版本签发至多五分钟的识别许可；前端携带原图片和许可直连独立 AI Service。跨服务器时间校验允许最多 30 秒的时钟偏差，许可自身的签发到过期时间仍不得超过五分钟。AI 再次校验真实管理员 JWT 和许可，业务后端在保存/发布时重新检查当前版本。

缺少签名配置时识别不可用，既有公开成绩和 AI 复盘不受影响。截图识别默认最多两个并发、每分钟最多 60 次准入，单次模型调用预算 90 秒。实际 provider 仍可能超时或识别不准；失败不会自动保存/发布，管理员可以重试。

## 存储与验证

赛事状态、军团、草稿/正式 snapshot 和审计保存在 Business PostgreSQL；截图在既有数据卷的赛事独立命名空间。未关联的上传附件 24 小时后清理，已关联草稿、正式记录或审计的证据随赛事保留。删除按本域 FK 和引用顺序执行，不删除 HoF、三环或其他赛事仍引用的附件。

关键验证包括按整轮配置闸门、精确积分及并列排名、重复上传/跨组冲突、版本冲突、正式/草稿隔离、最终确认幂等、清分和整天修正、真实 PostgreSQL migration/事务、图片 permit/gateway/JSON 解析，以及前端三语、路由和管理门禁。普通测试不调用付费 AI；真实识别准确率须另行明确执行 `ai-live` probe。
